# 校园实验室预约与审批系统：D00—D16 开发步骤总矩阵

## 1. 这套材料解决什么问题

这不是让非计算机专业学生独立编程的教材，也不是让学生点击一个“自动完成”按钮的教学平台。学生要亲手经历软件逐步形成的过程，但每一步需要的完整代码都由课程提供。

课堂中的固定动作只有六类：

1. 教师先说明本步解决什么问题、为什么现在要做。
2. 学生打开指定的源文件和项目中的目标文件。
3. 学生使用 `Ctrl+A`、`Ctrl+C`、`Ctrl+V` 完成“整文件复制替换”，不在某一行插入零散代码。
4. 学生按手册启动系统或运行测试。
5. 学生访问指定网址，完成一个有意义的操作，并与真实截图核对。
6. 若结果不一致，按本步的故障处理检查；仍未解决时，直接用本步“完整恢复包”恢复。

这意味着学生虽然不需要自己构思代码，但必须知道：复制了哪个文件、该文件承担什么职责、运行后增加了什么能力、怎样判断结果正确。

## 2. 版本与步骤的关系

- `dev-v0.1` 至 `dev-v1.0` 是七个正式功能版本，表示可讲解、可验收的阶段成果。
- `D00` 至 `D16` 是课堂开发检查点，表示从零到成品的 16 次连续操作。
- 正式版本只出现在 `D03、D05、D07、D10、D12、D14、D16` 七个终点。
- 其余 D 步骤是教学用的可运行中间状态，不另造正式版本号。
- 每个 D 文件夹保存“完成该步后的完整项目”，既是代码来源，也是课堂救援用的恢复包。

完整代码统一存放在：

## 5. 每一章固定写法

每章必须按下面的顺序出现，学生不需要猜下一步做什么：

### A. 本步先看懂

- 当前起点是什么。
- 当前系统缺少什么。
- 本步结束后会多出什么。
- 本步涉及哪些文件，各文件分别负责什么。
- 本步预计操作时间。

### B. 开始前检查

- 检查当前页面或命令输出，确认起点正确。
- 停止仍在运行的旧服务器。
- 明确本步源文件夹和学生项目目标文件夹的绝对/相对位置。

### C. 逐项操作

每个操作都必须同时写清：

1. 操作编号和目的。
2. 源文件准确路径。
3. 目标文件准确路径。
4. 是“新建”“整文件替换”还是“删除”。
5. 完整代码或可直接打开复制的完整文件。
6. 代码中关键教学注释的含义。
7. 保存后暂时会发生什么，是否需要立即运行。

### D. 运行与核对

- 使用哪个批处理或哪一条命令。
- 浏览器访问哪个完整网址。
- 需要点击、输入什么。
- 正确结果应出现哪些文字、数据或状态。
- 紧接着放置对应的真实运行截图，而不是示意图。

### E. 出错时怎么恢复

- 先检查的 3—5 个常见问题。
- 给出本步完整项目恢复包路径。
- 明确恢复动作：备份个人数据库（如需要）→ 清空本步误改文件 → 复制完整恢复包 → 重新初始化/启动。

### F. 本步完成标志

用三句话结束：学生现在能做什么、系统内部新增了什么、本步是哪个正式版本的组成部分。

## 6. 代码与文档制作规则

1. 每个步骤完成后都必须能独立启动，不能保留“下一步才修复”的语法错误或缺失依赖。
2. 每个步骤只增加一个可理解的功能结果；文件可以有多个，但它们共同服务于这一个结果。
3. 手册中不使用“在第 87 行插入下面三行”一类高风险操作，统一使用完整文件替换。
4. Python 代码对路由、模型、会话、查询、写库等首次出现的概念添加简短中文教学注释；注释解释原因和职责，不逐行翻译语法。
5. 正式终点 D03、D05、D07、D10、D12、D14、D16 的代码必须与七个 `版本终点核对包` 机械一致。
6. 每一步至少执行一次自动检查；正式版本终点必须运行该版本全部测试。
7. 所有截图从对应 D 步骤的真实代码启动后获取；截图内容、网址、账号和手册叙述必须一致。
8. 学生课堂上使用自己的项目副本；`教学资源/逐步开发代码/Dxx...` 只读，用于复制和恢复。
9. 暂不在这 16 章中穿插问题定义、可行性分析、需求分析、UML、系统设计和验收报告写作。这些材料在代码实操手册完成后单独补齐，再按课堂生命周期顺序编排。

## 7. 制作与验收顺序

材料制作严格按 `D00 → D01 → … → D16` 推进。每完成一步，必须同时完成以下四项才能进入下一步：

- 完整代码快照已生成；
- 从上一步按手册操作能够到达本步；
- 自动检查或正式测试已通过；
- 真实运行截图已放入手册并与文字核对。

这张矩阵是后续代码、操作手册和截图的唯一边界依据。若调整某一步功能，必须先修改本矩阵，再同步修改代码和手册，避免三套材料互相矛盾。
