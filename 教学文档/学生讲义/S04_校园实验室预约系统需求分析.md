# S04 校园实验室预约系统需求分析

## 1. 本章任务

S03已经确定项目“有条件可行”。本章进入需求分析，回答：

> 在已经确定的范围内，系统必须为哪些人提供什么能力，达到什么结果才算完成？

本章使用1课时，完成《学生项目开发记录册》第6—9节。最终要形成：

- 角色与核心用例表。
- REQ-01—REQ-10编号化需求清单。
- 关键业务规则。
- “学生提交实验室预约”核心用例说明。
- 每条需求的实现版本和可执行验收标准。

本章仍不编写业务代码，也不建立Git版本标签。

## 2. 需求不是功能名称的堆积

下面三种表达看起来都在谈预约，但质量不同。

```text
表达1：预约管理
表达2：做一个预约页面
表达3：已登录学生能够选择一个当前可用的实验室时段，填写用途、人数和联系方式后提交预约；提交成功后系统生成唯一预约编号并将状态设为待审批。
```

- 表达1只是模块名称，不知道谁使用、做什么、结果是什么。
- 表达2过早限定了页面，却没有说明业务结果。
- 表达3包含角色、前提、动作、数据和可检查结果，可以继续设计和测试。

一条可用需求通常包含：

```text
谁
＋在什么条件下
＋完成什么动作
＋系统产生什么可观察结果
```

## 3. 需求从哪里来

本案例的需求不能凭程序员想象产生，而要回到S03识别的四类利益相关者和问题证据。

| 来源 | 关心的问题 | 形成的需求方向 |
| --- | --- | --- |
| 学生 | 找得到实验室、交得上申请、看得到结果 | 查询、提交、查看、取消 |
| 审批教师 | 信息完整、申请可处理、不能重复审批 | 审批队列、详情、通过、驳回 |
| 实验室管理员 | 服务状态准确、不能破坏已有预约 | 实验室启停及冲突规则 |
| 系统维护者 | 能运行、能定位、能确认版本 | 环境锁定、测试、健康与版本信息 |
| 项目边界 | 32课时、本地运行、教学数据 | 不加入统一认证、通知和分布式部署 |

需求分析是在不同诉求和项目边界之间形成明确约定。

## 4. 功能需求与非功能需求

### 4.1 功能需求

功能需求说明系统应提供的业务行为。例如：

> 审批教师能够查看待审批申请，并对申请作出通过或驳回决定。

它通常可以用“谁能够做什么”描述。

### 4.2 非功能需求

非功能需求说明系统完成这些行为时必须具备的质量或约束。例如：

> 未登录用户和错误角色不能访问受保护功能；所有修改数据的表单必须验证防伪令牌。

“界面友好”“系统安全”“速度快”都太模糊。必须说明用什么现象或测试判断是否达到要求。

### 4.3 业务规则

业务规则是无论页面怎样设计都必须遵守的条件。例如：

> 待审批或已通过的预约占用对应时段；该时段不能再次预约。

它不一定单独成为一个页面，却会同时影响查询、提交、审批、取消和实验室启停。

## 5. 先确定角色和用例

“角色”代表一类责任和权限，不等于某个具体姓名。

| 角色 | 核心用例 | 成功结果 |
| --- | --- | --- |
| 未登录访客 | 访问首页、浏览实验室、登录 | 可以了解系统和公开实验室信息 |
| 学生 | 查询时段、提交预约、查看自己的预约、取消预约 | 申请进入审批流程并能追踪结果 |
| 审批教师 | 查看审批队列、查看申请详情、通过或驳回 | 待审批申请得到一次有效处理 |
| 实验室管理员 | 查看实验室状态、设为维护中、恢复开放 | 服务状态变化符合预约约束 |
| 系统维护者 | 执行测试、查看健康与版本信息 | 能确认系统是否可运行及当前版本 |

### 操作1：填写角色与核心用例

打开个人《学生项目开发记录册》第6节，填写五类角色。每一行都使用“动词＋对象”描述用例，例如“查看自己的预约”，不要只写“预约模块”。

可见结果：每类角色至少有一个用例，每个成功结果都能从页面、状态或接口中观察。

本操作只修改个人记录册，不修改代码；无需恢复。

| REQ-10 | 非功能 | P1 | 系统应能在普通Windows笔记本本地部署，并提供依赖版本、系统版本和健康状态证据 | dev-v1.0 | 使用锁定依赖可启动；`/version`显示版本；`/health`返回正常JSON；发布提交和`dev-v1.0`标签一致 |

### 6.1 优先级含义

- **P0**：没有它就不能形成正确的核心业务，必须优先完成。
- **P1**：不阻止最早的业务演示，但属于V1.0约定成果，仍必须完成。

P1不是“有时间才做”。它表示开发顺序可以晚于P0，而不是可以从验收中删除。

### 6.2 为什么需求要写首次完整实现版本

一个需求可能先有原型，后面再完善。例如REQ-01在V0.1先出现静态实验室信息，V0.2开始从数据库读取。表中记录“首次完整实现版本”，后续版本仍必须保留该功能。

把上表REQ-01—REQ-10填写到记录册第7节。填写时完成两项动作：

1. 不改变编号、核心含义和版本归属。
2. 用自己的话缩写需求，但验收标准必须仍然能够执行。

可见结果：10个编号无遗漏、无重复；每一行都有类型、优先级、版本和验收标准。

## 8. 用例把多条需求组织成一段业务

用例描述一个角色为了获得业务结果，与系统进行的一系列交互。它比单条需求更完整，但不讨论具体Python函数怎样写。

### 8.1 核心用例：学生提交实验室预约

| 项目 | 内容 |
| --- | --- |
| 用例编号 | UC-01 |
| 用例名称 | 学生提交实验室预约 |
| 主要参与者 | 学生 |
| 前置条件 | 学生已登录；实验室可预约；所选时段开放且未被有效预约占用 |
| 触发事件 | 学生在实验室详情中选择一个可用时段 |
| 基本流程 | 1. 系统显示时段和预约表单；2. 学生填写用途、人数、联系方式；3. 系统校验数据和时段；4. 系统生成唯一编号；5. 保存待审批预约和创建历史；6. 显示预约详情 |
| 异常流程A | 输入不符合RULE-03时，显示全部相关错误，不保存预约 |

| 异常流程C | 当前用户不是学生时，拒绝访问 |
| 后置条件 | 成功时新增一条待审批预约和一条状态历史；该时段暂时不可再次预约；失败时数据库不新增预约 |

### 8.2 为什么必须写异常流程

只写“选择—填写—提交成功”，得到的是演示脚本，不是完整需求。软件最常见的错误恰恰发生在无效输入、重复操作、越权访问和状态冲突中。

### 操作4：完成核心用例

填写记录册第9节。基本流程必须使用编号步骤；异常流程至少写三种；后置条件同时说明成功和失败时数据应怎样变化。

完成后，用彩笔或文字标出基本流程中分别对应REQ-02、REQ-03、REQ-04和REQ-08的步骤。

本操作只修改个人记录册，不修改代码；无需恢复。

## 9. 怎样写可执行的验收标准

验收标准不是“功能已完成”，而是可以照着执行并判断通过或失败的条件。

可以使用“给定—当—那么”结构：

```text
给定：学生账号已经登录，某时段处于可预约状态
当：填写合法用途、人数和联系方式并提交
那么：系统生成预约编号，状态为待审批，并在“我的预约”中显示
```

再看一个异常标准：

```text
给定：实验室容量为40人
当：学生填写41人并提交
那么：系统提示人数必须在1—40之间，数据库中不新增预约
```

合格标准应具备：

- 明确前置状态。
- 明确用户操作或输入。
- 明确页面、状态码或数据变化。
- 任何同学重复执行都能得到同样的通过/失败判断。

## 11. 需求评审：在开发前发现问题
