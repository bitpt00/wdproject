# S03 软件生命周期、问题定义与可行性分析

## 1. 本章任务

环境和版本管理解决了“项目怎样运行、变化怎样保存”的问题。现在回到软件开发真正的起点：

> 先证明存在一个值得解决的问题，再判断计划中的软件是否值得做、能否做成。

本章使用2课时，完成《学生项目开发记录册》第3—5节。完成后应形成：

1. 一句话项目定义。
2. 利益相关者与问题证据表。
3. 可检查的项目目标。
4. 范围内、范围外和约束条件。
5. 两种技术方案比较。
6. 技术、经济、操作和时间可行性判断。
7. 主要风险及“可行、不可行或有条件可行”的结论。

本章不编写业务代码，也不建立新Git标签。

## 2. 先看完整的软件生命周期

软件项目不是“想到功能后马上写代码”。本课程采用一个简化但完整的生命周期：

```mermaid
flowchart LR
    A[问题定义<br/>为什么做] --> B[可行性分析<br/>能不能做]
    B --> C[需求分析<br/>必须做什么]
    C --> D[系统设计<br/>准备怎样做]
    D --> E[增量开发<br/>逐版实现]
    E --> F[软件测试<br/>是否正确]
    F --> G[验收发布<br/>是否可交付]
    G --> H[运行维护<br/>持续改进]
```

| 阶段 | 必须回答的问题 | 本课程中的主要证据 |
| --- | --- | --- |
| 问题定义 | 为什么需要这个系统 | 问题、目标、利益相关者和范围 |
| 可行性分析 | 在现有条件下值得做、做得成吗 | 方案比较、四类可行性和风险 |
| 需求分析 | 用户和业务要求系统做什么 | REQ编号、用例、业务规则、验收标准 |
| 系统设计 | 用什么结构实现需求 | 架构、模块、页面、数据和UML图 |
| 增量开发 | 怎样从起点可靠到达终点 | V0.1—V1.0七次版本升级 |
| 软件测试 | 正常和异常情况下是否正确 | 手工用例、自动测试和缺陷记录 |
| 验收发布 | 是否达到交付条件 | 需求追踪、端到端验收和发布标签 |

这些阶段不是只能单向执行的流水线。测试发现需求理解错误时，必须回到需求；开发发现设计无法实现时，也要修正设计。生命周期的价值是让关键问题不被遗漏，而不是禁止反馈。

## 3. AI时代，生命周期是否还需要

AI可以更快地产生需求草稿、图、代码和测试，但“产生得快”不等于“结果正确”。下面的责任没有消失：

- 人决定问题是否真实、范围是否合理。
- 人确认不同用户真正需要什么。
- 人选择适合当前条件的技术方案。
- 人判断AI生成的代码是否满足业务规则。
- 人通过测试和验收为结果负责。

因此，本课程先手工经历完整过程，第四天再使用AI。只有先知道每个阶段应产生什么证据，才能判断AI输出缺少了什么、错在什么位置。

## 4. 问题、目标、需求和方案不能混写

这四个概念经常出现在同一段话中，但回答的问题不同。

| 概念 | 回答的问题 | 本案例示例 |
| --- | --- | --- |
| 问题 | 当前有什么困难和影响 | 预约信息分散，申请人不能及时知道处理状态 |
| 目标 | 项目希望改善到什么程度 | 让申请、审批和结果查询形成可追踪闭环 |
| 需求 | 系统必须提供什么能力 | 学生能够查看自己提交的预约及当前状态 |
| 方案 | 准备使用什么方式实现 | 使用Flask、Jinja2和SQLite构建本地Web系统 |

下面是一条不合格的问题定义：

> 我们的问题是还没有使用Flask开发预约系统。

它把技术方案误写成了问题。即使不用Flask，预约信息分散、状态不透明等业务困难仍然存在。

## 5. 案例背景：没有系统时怎样预约

为便于全班使用相同材料，本课程采用以下**案例设定**。这些内容是教学案例，不冒充学校真实调研数据。

当前实验室预约主要依靠即时消息、电话和人工表格：

```text
学生询问实验室是否可用
→ 管理人员查找课表或登记表
→ 学生把用途、时间和人数发给管理人员
→ 管理人员转给教师确认
→ 教师回复通过或不通过
→ 管理人员再把结果通知学生
```

从这个过程可以观察到四类典型问题：

| 编号 | 现象 | 直接影响 |
| --- | --- | --- |
| P-01 | 可用实验室和时段分散在不同消息或表格中 | 学生反复询问，管理人员重复回答 |
| P-02 | 申请内容格式不统一，可能缺少用途、人数或联系方式 | 审批前需要来回补充信息 |
| P-03 | 申请、审批意见和状态分散在聊天记录中 | 学生不清楚进度，历史过程难追踪 |
| P-04 | 实验室维护状态与预约信息没有统一校验 | 可能继续预约维护中的实验室，或错误停用已有预约的实验室 |

问题证据不能只写“麻烦”“体验不好”。应当写清可观察的现象、受影响的人和造成的后果。

## 6. 识别利益相关者

利益相关者是会使用系统、受到系统影响，或对系统有管理责任的人。

| 利益相关者 | 关心的问题 | 系统中的主要能力 |
| --- | --- | --- |
| 学生 | 哪间实验室可用、申请是否成功、何时有结果 | 查询、提交、查看和取消自己的预约 |
| 审批教师 | 申请信息是否完整、是否符合使用要求 | 查看待审批申请，通过或驳回并填写意见 |
| 实验室管理员 | 实验室是否开放、维护状态是否与预约冲突 | 查看状态，安全地设为维护或恢复开放 |
| 系统维护者 | 系统能否部署、出现问题如何定位、版本是否清楚 | 环境清单、测试、健康检查和版本信息 |

不能只采访最终点击按钮的人。例如，管理员虽然不提交预约，但实验室启停规则直接影响系统能否正确运行。

### 操作1：填写利益相关者表

1. 复制`教学资源\学生项目开发记录册模板.md`到个人学习成果目录。
2. 文件名改为`学号_姓名_学生项目开发记录册.md`。
3. 建议保存在代码目录之外，例如：

   ```text
   D:\software-course\learning-results
   ```

4. 打开记录册第3节。
5. 根据上表，用自己的话填写四类人员当前怎样工作、遇到什么困难、希望获得什么能力。

可见结果：第3节四行均有具体内容，不能只写“方便”“提高效率”。

恢复方法：记录册是个人成果。如果误删模板结构，从教学资源重新复制一份，再把已经完成的内容迁回对应栏目。

## 7. 写出合格的一句话项目定义

推荐使用下面的句式：

```text
为了解决【现有问题】，面向【主要用户】，建设一个能够【核心业务结果】的【系统名称】。
```

本案例的基准表达为：

> 为了解决校园实验室预约信息分散、申请格式不统一和审批状态难追踪的问题，面向学生、审批教师和实验室管理员，建设一个能够完成实验室查询、预约申请、教师审批和状态管理闭环的校园实验室预约与审批系统。

判断是否合格可以问三个问题：

1. 不提技术名称，别人能否理解为什么要做？
2. 是否指出了主要服务对象？
3. 是否描述业务结果，而不是罗列页面按钮？

### 操作2：完成问题定义

在记录册第4.1—4.3节完成：

- 用3—6步描述原有预约过程。
- 至少填写P-01、P-02、P-03三条问题证据。
- 写出一句话项目定义。

完成后让相邻同学只读这一句话，并回答“谁遇到了什么问题、系统准备产生什么结果”。如果不能回答，应重新修改句子。

本操作只修改个人记录册，不修改代码；无需恢复。

## 8. 把目标写成可以检查的结果

“系统更方便”“提高管理水平”无法直接验收。目标应当能由页面、数据或测试结果检查。

| 目标编号 | 可检查的目标 | 检查方法 |
| --- | --- | --- |
| OBJ-01 | 学生能够查询开放的实验室和可选时段 | 在实验室列表与详情页执行查询 |
| OBJ-02 | 一次预约从提交到审批结果形成完整状态链 | 用学生和教师账号完成端到端流程 |
| OBJ-03 | 不同角色只能访问自己有权使用的功能 | 用三类账号执行权限测试 |
| OBJ-04 | 主要正常流程和异常规则有重复可执行的检查 | 运行自动测试并查看通过数量 |

目标描述“项目结束后可证明的变化”，具体字段和页面留到需求分析与设计阶段确定。

### 操作3：填写项目目标

在记录册第4.4节至少填写三个目标，每个目标都必须有检查方法。

自检方法：如果检查方法只能写“感觉更方便”，目标仍然不够具体。

本操作只修改个人记录册，不修改代码；无需恢复。

## 9. 用范围控制项目大小

范围回答“这次项目承诺做什么、不做什么”。明确范围外事项不是偷工减料，而是避免一个小项目无限膨胀。

### 9.1 本课程的范围内事项

- 浏览实验室、按关键词和状态筛选、查看详情和时段。
- 使用预置演示账号登录、退出并区分三类角色。
- 学生提交、查看和取消自己的预约。
- 审批教师通过或驳回待审批申请。
- 保存预约状态变化历史。
- 管理员在业务规则允许时启停实验室。
- 输入校验、权限控制、错误页面、自动测试、健康检查和版本信息。
- 在一台个人电脑上运行SQLite数据库和Web服务。

### 9.2 本课程的范围外事项

- 与学校统一身份认证平台真实对接。
- 短信、微信、邮件或移动App通知。
- 门禁设备、传感器和实验室硬件联动。
- 收费、财务结算和电子发票。
- 多校区、高并发和分布式部署。
- 面向真实生产环境的备份、监控和运维平台。
- 自助注册、找回密码和复杂组织机构管理。

这些功能并非没有价值，而是不属于本次32课时教学项目的承诺。

### 9.3 约束条件

| 类型 | 本项目约束 |
| --- | --- |
| 时间 | 4天、32课时完成手工全过程和AI辅助实践 |
| 人员 | 每人独立完成，不依靠小组分工 |
| 技术 | Python 3.11、Flask/Jinja2、SQLite，本地浏览器使用 |
| 设备 | 普通Windows笔记本，不搭建独立数据库服务器 |
| 数据 | 使用教学演示账号和种子数据，不处理真实敏感数据 |
| 开发方式 | 固定起点、固定终点，按实验步骤增量完成 |

### 操作4：填写范围与约束

在记录册第4.5节至少填写5项范围内事项和4项范围外事项；在第4.6节填写时间、技术、设备、人员和数据约束。

检查方法：范围内的每一项都应在后续七个版本中找到归属；范围外事项不应悄悄出现在验收要求中。

本操作只修改个人记录册，不修改代码；无需恢复。

## 10. 可行性分析不是简单写“可行”

可行性分析应当形成下面的推理链：

```text
现有条件和证据
→ 可能的困难与风险
→ 是否有可执行的应对措施
→ 在哪些前提下可行
```

本课程使用四个最常见、最容易理解的维度。

### 10.1 技术可行性

要检查：

- 普通笔记本能否运行所选技术。
- 学生现有基础能否理解和操作。
- 依赖是否能够安装并固定版本。
- 数据库、页面、后端和测试是否能在规定时间内集成。

证据来自S01：Python 3.11、虚拟环境和锁定依赖已在本机验证，系统能够通过本地浏览器访问。

### 10.2 经济可行性

教学原型使用的Python、Flask、SQLite和Git无需额外购买软件许可；系统运行在已有笔记本上，不新增数据库服务器。主要投入是课程时间、教师准备和学生操作时间。

这不等于真实生产系统“没有成本”。生产部署还会有服务器、运维、安全、培训和持续维护成本，只是这些属于本次课程范围外。

### 10.3 操作可行性

三类用户都通过浏览器操作，业务顺序与现实职责接近；不要求用户使用开发工具。主要风险是角色混淆和表单信息填写错误，可以通过角色工作台、权限限制、明确提示和输入校验降低。

### 10.4 时间可行性

如果要求非计算机专业学生从空白文件独立写出全部代码，32课时不可控。本课程采用七个固定起点和终点、完整代码步骤、逐版检查与故障救援，因此能够把时间集中在理解过程、观察结果和验证功能上。

## 11. 比较两种技术路线

技术方案必须根据当前目标和约束选择，不能只比较“哪一种更高级”。

| 比较项 | Flask+Jinja2+SQLite | Spring Boot+Vue+MySQL |
| --- | --- | --- |
| 主要语言和组件 | Python、HTML模板、本地数据库 | Java、JavaScript、前端工程、后端工程、数据库服务 |
| 首次安装 | Python和依赖包 | JDK、构建工具、Node.js、前端依赖、MySQL等 |
| 前后端连接 | 服务器直接渲染页面，链路较短 | 前后端通过API连接，链路较长 |
| 数据库维护 | 单个SQLite文件，无独立服务 | 需要安装、启动和配置MySQL服务 |
| 适合本课程 | 容易看见完整流程，故障点较少 | 32课时内环境和框架学习量较大 |
| 大型团队扩展 | 可以扩展，但需进一步重构和部署设计 | 更容易建立明确前后端分工和企业级结构 |

本课程选择Flask+Jinja2+SQLite，不是因为另一条路线错误，而是因为当前目标是让非计算机专业学生在有限时间内经历完整生命周期，并真正运行、修改和测试一个系统。

### 操作5：完成技术方案比较

填写记录册第5.1节。每个比较项都要写两种方案的事实，最后一列说明该事实为何支持当前选择。

不合格写法：

```text
Flask好，Spring Boot不好。
```

合格写法：

```text
本课程只有32课时且学生编程基础有限。Flask方案安装组件更少、页面到数据库链路更短，因此更适合本次教学原型；这不代表它在所有项目中都优于前后端分离方案。
```

本操作只修改个人记录册，不修改代码；无需恢复。

## 12. 识别主要风险

风险是“尚未发生，但一旦发生会影响目标”的不确定事件。已经发生的端口冲突属于问题；“课堂中可能出现端口冲突并拖慢进度”才是风险。

| 风险编号 | 风险事件 | 可能性 | 影响 | 应对措施 |
| --- | --- | --- | --- | --- |
| R-01 | 个别电脑无法正确安装Python或依赖 | 中 | 高 | 课前检查；锁定版本；提供手工命令和故障定位表 |
| R-02 | 复制代码时漏行、缩进错误或放错文件 | 高 | 中 | 使用完整文件；每步运行；终点机械比对 |
| R-03 | 前一版本未完成导致后续版本无法继续 | 中 | 高 | 每版设门禁；保留教师起点包；先恢复到正确起点 |
| R-04 | 学生只看到页面结果，没有理解生命周期 | 中 | 高 | 每版记录问题、需求、设计、测试和Git证据 |
| R-05 | 本地旧数据库使页面结果与预期不一致 | 中 | 中 | 明确数据库位置；需要时使用规定的重建步骤 |

风险应对措施必须是能执行的动作。“加强重视”“认真检查”通常不够具体。

### 操作6：填写风险表

在记录册第5.2节至少填写三个风险：一个环境风险、一个代码操作风险和一个进度风险。用高、中、低描述可能性与影响，并写出实际可执行的预防或应对措施。

本操作只修改个人记录册，不修改代码；无需恢复。

## 13. 作出有边界的可行性结论

本案例的推荐结论是：

> **有条件可行。**在使用Python 3.11、Flask/Jinja2、SQLite、预置教学数据、七个固定版本和逐版检查的前提下，普通笔记本可以在32课时内完成教学原型并经历完整开发过程。该结论只适用于本地教学和功能验证，不表示V1.0可以未经安全、性能、真实身份认证和生产运维改造就直接用于全校正式运行。

这个结论包含四个部分：

1. 明确判断：有条件可行。
2. 成立条件：技术、数据、版本和教学方式。
3. 判断依据：环境实测与工作量控制。
4. 适用边界：教学原型，不等于生产系统。

### 操作7：完成并核对提交成果

1. 填写记录册第5节四类可行性。
2. 填写技术方案比较和至少三个风险。
3. 用一段完整文字给出可行性结论。
4. 保存记录册。
