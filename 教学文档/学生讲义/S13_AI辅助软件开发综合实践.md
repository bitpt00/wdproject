# S13 AI辅助软件开发综合实践：独立完成一个同类小系统

## 1. 本实践的固定起点、终点和成果

| 项目 | 内容 |
| --- | --- |
| 生命周期位置 | 第二次完整迭代：AI辅助的问题、需求、设计、开发、测试与发布 |
| 起点 | `教学资源\AI项目S0起点包`的3个文件，加一个新的个人Git仓库 |
| 终点 | 每人一个可运行、可测试、可解释的同类小系统`ai-v1.0` |
| 技术路线 | Python 3.11、Flask 3.1.3、Jinja2、Flask-SQLAlchemy 3.1.1、SQLite、pytest 9.1.1 |
| 实施方式 | 一人一项目；AI生成建议和代码，学生决定、运行、检查、修正和说明 |
| 课时 | 第25—32课时，共360分钟 |
| 最少版本 | `ai-s0`、`ai-v0.1`、`ai-v0.2`、`ai-v0.3`、`ai-v1.0` |
| 最少测试 | 10项，其中至少1项核心流程测试、2项异常输入测试、2项权限测试 |

最终交付物不是一段AI对话，也不是一张网页截图，而是：

```text
问题和范围
＋ 6—8条可验收需求
＋ 简明设计和版本路线
＋ 5个可查看的Git基线
＋ 能启动的完整源码
＋ 至少10项通过的测试
＋ 1条真实缺陷闭环
＋ README和ai-v1.0发布标签
＋ AI使用记录与人工审查结论
```

本实践没有全班统一的最终代码，因为每人的题目和AI输出不同。代码完整性通过“每轮要求完整文件、每版Git提交、最终干净克隆复测”验证，而不是用一份答案覆盖所有学生。

## 2. 为什么先手工经历七个版本，再使用AI

在前24课时中，你已经亲自观察过一个软件怎样从静态页面逐渐增加数据库、登录、业务状态、测试和发布。现在使用AI，不是跳过这些过程，而是把你的角色从“按教师给定步骤实现”提高为“向AI说明目标并审核结果”。

| 活动 | 手工引导阶段 | AI辅助阶段 |
| --- | --- | --- |
| 问题和范围 | 教师给出校园实验室案例 | 学生选择小题目并控制范围 |
| 需求 | 阅读统一REQ-01—REQ-10 | 学生编写6—8条需求，AI只能协助检查 |
| 设计 | 阅读统一架构和UML | AI提建议，学生删除多余设计并定版 |
| 代码 | 按固定文件逐步复制和理解 | AI按小版本生成完整文件，学生逐项验证 |
| 测试 | 执行教师给定测试并学习设计 | 学生先写验收标准，再要求AI生成测试并补漏 |
| 缺陷 | 按讲义复现 | 学生把自己的真实错误交给AI分析并验证修复 |
| 发布 | 对照统一V1.0 | 学生用自己的测试、追踪表和Git标签作出决定 |

AI可能快速生成大量代码，也可能漏掉需求、虚构依赖、改坏旧功能或声称“已经测试”却没有在你的电脑上运行。最终责任始终属于操作和提交代码的人。

## 3. 先把项目规模锁住

### 3.1 三个推荐题目

每人任选一个，也可提出同等规模的校园题目，经教师确认后使用：

| 题目 | 两类登录角色 | 最多3个核心实体 | 一条核心业务主线 |
| --- | --- | --- | --- |
| A 社团活动报名与审核系统（默认） | 学生、活动负责人 | User、Activity、Registration | 学生报名→负责人通过/驳回→学生查看或取消 |
| B 校园设备报修与处理系统 | 报修人、维修人员 | User、RepairTicket、TicketHistory | 学生报修→维修人员受理/完成→学生查看进度 |
| C 校园失物招领与认领系统 | 学生、管理员 | User、Item、Claim | 学生发布/申请认领→管理员确认→双方查看结果 |

如果10分钟内不能确定题目，直接选择A，不把课堂时间消耗在寻找“最有创意”的主题上。

### 3.2 必须遵守的规模上限

- 只做一个Web应用，不做手机App、小程序和前后端分离。
- 登录角色最多2类，核心数据实体最多3个。
- 只保留1条核心状态流程，状态最多4种。
- 编号化需求6—8条，页面4—8个。
- 不使用文件上传、短信、邮件、支付、地图、外部API和实时聊天。
- 只使用起点包的3个Python依赖，不让AI随意更换框架。
- 使用预置演示账号和虚构数据，不输入真实密码、身份证、手机号、访问令牌或学校内部数据。

范围越大，AI一次生成的文件越多，学生越难发现它在哪一处误解了业务。本实践评价完整闭环和验证证据，不评价功能数量。

### 3.3 默认题目可直接使用的范围

选择A时，可直接采用下面的范围：

```text
系统名称：校园社团活动报名与审核系统
要解决的问题：活动信息和报名状态分散，学生不知道是否报名成功，负责人难以统一审核
角色：学生、活动负责人
核心实体：User、Activity、Registration
状态：PENDING、APPROVED、REJECTED、CANCELLED
范围内：活动列表/详情、登录、报名、我的报名、审核、取消、测试和发布
范围外：在线支付、消息推送、文件上传、签到、学分认定和移动端
```

其他题目也必须能用同样简短的文字说清楚。

## 4. 建立AI项目的固定S0起点

### 4.1 新建独立目录

不要在已经完成的`campus-lab-development`中让AI直接改代码。新建一个不含空格的目录，例如：

```powershell
$courseRoot = "D:\course-materials\campus-lab-development"
$aiProjectRoot = "D:\student-work\ai-campus-app"
New-Item -ItemType Directory -Path $aiProjectRoot
Copy-Item -LiteralPath "$courseRoot\教学资源\AI项目S0起点包\.gitignore" -Destination $aiProjectRoot
Copy-Item -LiteralPath "$courseRoot\教学资源\AI项目S0起点包\requirements.txt" -Destination $aiProjectRoot
Copy-Item -LiteralPath "$courseRoot\教学资源\AI项目S0起点包\初始化开发环境.bat" -Destination $aiProjectRoot
Set-Location $aiProjectRoot
```

把两个路径改成自己的实际目录。若目标目录已存在，不执行`New-Item`覆盖；换一个新目录或先请教师检查。

### 4.2 创建独立虚拟环境

```powershell
.\初始化开发环境.bat
.\.venv\Scripts\python.exe --version
.\.venv\Scripts\python.exe -m pip check
.\.venv\Scripts\python.exe -c "from importlib.metadata import version; print(version('Flask')); print(version('Flask-SQLAlchemy')); print(version('pytest'))"
```

预期Python为3.11.x，`pip check`显示没有依赖冲突，三个库均可导入。这个`.venv`只属于AI项目，不影响手工项目和全局Python。

### 4.3 建立`ai-s0`

```powershell
git init -b main
git add .gitignore requirements.txt 初始化开发环境.bat
git commit -m "chore: initialize AI project workspace"
git tag -a ai-s0 -m "AI project fixed starting point"
git status --short
git ls-files
```

预期工作区干净，跟踪文件恰好3个，`.venv`不出现。把AI项目路径和`ai-s0`提交号写入记录册第22节。

操作之后理解：AI项目使用新仓库，是为了让每轮生成和修复都可比较、可撤销，不让实验影响已经验收的校园实验室系统。

### 4.4 起点恢复方法

AI第一次输出失败时，不要重新复制整个课程项目。在保存错误信息后执行：

```powershell
git stash push --include-untracked -m "failed AI attempt before ai-v0.1"
git status --short
```

失败文件会进入可恢复的stash，工作区回到`ai-s0`。用`git stash list`仍能查看，不会直接丢失证据。

## 5. 与AI协作时始终使用同一份“工作约定”

每次开始新的AI对话，先发送下面这段；把方括号内容换成自己的项目：

```text
你是我的软件开发助手，但不能替我决定需求或声称已经在我的电脑上运行。

项目：[系统名称]
使用者：[角色1、角色2]
技术栈固定为：Windows、Python 3.11、Flask 3.1.3、Jinja2、Flask-SQLAlchemy 3.1.1、SQLite、pytest 9.1.1。
不使用Vue、React、Node.js、MySQL、Docker或任何新增第三方库。

协作规则：
1. 每次只完成我指定的当前版本，不提前加入后续功能。
2. 先复述本轮起点、目标、验收标准和将修改的文件；等我确认后再给代码。
3. 给代码时按文件路径输出每个新增或修改文件的完整内容，不用省略号，不说“其余不变”来代替所需代码。
4. 保持未列入本轮的文件和旧功能不变。
5. 同时给出Windows PowerShell运行命令、预期页面结果和pytest检查。
6. 不虚构执行结果；所有“通过”由我在本机运行后确认。
7. 发现信息不足时列出假设，不自行扩大范围。
8. 表单在服务端校验；密码使用Werkzeug哈希；权限在路由端检查；测试使用临时SQLite。
9. 所有界面和错误提示使用简体中文，变量和函数使用清楚的英文名。
```

这段约定解决“怎么合作”；每轮还要补充真实需求、当前目录和错误信息。只发送“帮我做一个管理系统”会让AI替你猜测几乎所有重要决定。

## 6. 第25课时：先比较，不急着生成代码

### 6.1 观察同一问题的两种提问

先向AI发送：

```text
帮我做一个社团活动报名系统。
```

只阅读回答，不复制代码。记录AI自行猜测了哪些内容，例如角色、字段、状态、技术栈和页面。

再发送第5节工作约定和第3.3节完整范围，要求它只列出仍需确认的问题，不写代码。比较两次回答：具体上下文是否减少了无关功能和错误假设。

### 6.2 人工必须保留的五项决定

1. 真正要解决的问题是什么。
2. 哪些功能属于本次范围。
3. 每条需求怎样验收。
4. AI输出是否符合需求和已有代码。
5. 测试结果是否足以允许发布。

把比较结果写入记录册第25节“手工开发与AI开发比较”。此时项目仍应停在`ai-s0`，没有业务代码。

## 7. 第26课时：问题定义、需求和验收标准

### 7.1 先由学生填写任务单

在记录册第22节填写：

| 项目 | 必须填写的内容 |
| --- | --- |
| 系统名称 | 一个具体校园小系统名称 |
| 要解决的问题 | 谁在什么过程中遇到什么困难 |
| 使用角色 | 最多2类 |
| 核心业务 | 用3—5步说明一条完整流程 |
| 明确不做 | 至少4项范围外功能 |

### 7.2 形成6—8条需求

所有题目至少覆盖以下六类，名称和业务词可替换：

| 需求编号 | 最小内容 | 可检查的验收标准示例 |
| --- | --- | --- |
| AI-REQ-01 | 访客浏览列表和详情 | 列表有种子数据；合法编号显示详情；不存在编号404 |
| AI-REQ-02 | 用户登录、退出和角色区分 | 正确账号登录；错误密码不建立会话；错误角色403 |
| AI-REQ-03 | 主要角色提交核心业务数据 | 合法输入生成唯一记录和初始状态 |
| AI-REQ-04 | 次要角色处理该记录 | 只能处理允许状态；结果和意见可追踪 |
| AI-REQ-05 | 主要角色查看并在规则允许时取消 | 只能操作本人数据；取消后状态正确 |
| AI-REQ-06 | 质量与发布 | 服务端校验、错误页、至少10项测试、README、版本和标签齐全 |

允许增加AI-REQ-07和AI-REQ-08，但不能用“界面美观”“功能完善”这类无法判断通过与否的表述。

### 7.3 让AI做审查，不让AI替你偷偷扩充

```text
下面是我已经确定的问题、范围和需求：[粘贴自己的内容]

请只做需求审查，不写代码：
1. 找出含糊、不可测试、彼此冲突或超过一日开发规模的内容。
2. 对每个问题说明原因并给出精简建议。
3. 不新增角色、实体、外部服务或范围外功能。
4. 最后输出一张“需求编号—验收标准—计划版本”表，供我人工确认。
```

逐项决定“接受、修改或拒绝”AI建议并记录理由。最终需求由学生定版，AI的原回答不能直接当需求文档。

### 7.4 本课时完成门禁

- 项目可用一句话定义；
- 角色不超过2类，实体不超过3个；
- 6—8条需求均有可执行验收标准；
- 每条需求分配到`ai-v0.1`—`ai-v1.0`；
- 范围外至少4项；
- 教师确认规模后才进入设计。

未通过时不生成代码。

## 8. 第27课时：让AI提出设计，由学生做减法

### 8.1 设计提示词

```text
当前基线：ai-s0，只有.gitignore、requirements.txt和初始化脚本。
已确认需求：[粘贴AI-REQ清单和验收标准]

请提出最小系统设计，不写业务代码，输出：
1. 页面与导航表：页面、角色、入口、核心内容。
2. 路由表：HTTP方法、URL、函数名、权限、成功结果、错误结果。
3. 数据模型表：最多3个实体，每个字段的类型、是否必填、关系。
4. 一条核心活动流程和状态转换表。
5. 文件树。
6. 四个版本的增量计划，每版列出新增/修改文件和验收方法。

检查约束：保持Flask+Jinja2+SQLite单体结构；不新增依赖；页面4—8个；状态最多4种。
```

### 8.2 用六个问题人工审查

| 检查问题 | 不合格表现 |
| --- | --- |
| 每条需求有实现位置吗 | 某需求没有页面、路由或数据支撑 |
| 每个页面有使用者吗 | AI生成“后台大屏”等无人提出的页面 |
| 每个字段来自业务吗 | 增加照片、地址、积分等范围外字段 |
| 状态转换明确吗 | 任意状态都能跳到任意状态 |
| 权限在服务器端吗 | 只隐藏按钮，没有路由检查 |
| 版本是增量的吗 | 第一版就一次生成最终系统 |

删除多余内容后，把最终页面、路由、实体、状态和版本表写入记录册。至少画用例图、类图和状态图中的两张；可让AI生成Mermaid文本，但必须逐条与定版设计核对。

### 8.3 固定四个终点

| 版本 | 起点 | 终点最低能力 | 最少自动测试 |
| --- | --- | --- | ---: |
| `ai-v0.1` | `ai-s0` | Flask可启动；首页和静态列表可打开；公共导航完成 | 2 |
| `ai-v0.2` | `ai-v0.1` | SQLite模型和种子数据；列表、筛选或详情来自数据库 | 4 |
| `ai-v0.3` | `ai-v0.2` | 两角色登录；核心记录可提交、处理和查看 | 8 |
| `ai-v1.0` | `ai-v0.3` | 校验、权限、异常、README、端到端验收和发布 | 10 |

各版可以超过最低测试数，但不能减少门禁或把所有代码留到最后一次生成。

## 9. 第28课时上半段：从`ai-s0`到`ai-v0.1`

### 9.1 本轮提示词

```text
当前起点：ai-s0，当前跟踪文件只有.gitignore、requirements.txt、初始化开发环境.bat。
当前目标：只完成ai-v0.1静态可运行骨架。
本版验收：
- app.py可启动在127.0.0.1:5000；
- 首页和静态列表页返回200；
- Jinja2使用base.html继承；
- CSS能加载；
- tests/test_app.py至少2项测试通过；
- 提供启动系统.bat和运行测试.bat。
本版不做：数据库、登录、提交、审批、管理员和外部API。

请先列出将创建的文件和页面；我确认后，再按文件路径给出每个文件的完整内容及PowerShell检查命令。
```

### 9.2 文件逐个落地，不整段盲贴

AI给出代码后按顺序操作：

1. 先核对它是否偷偷新增依赖或后续功能。
2. 每次只创建一个文件，完整复制，不把Markdown围栏复制进源码。
3. 创建`app.py`后先执行语法检查。
4. 创建模板和CSS后启动浏览器检查。
5. 最后创建测试并执行。

```powershell
.\.venv\Scripts\python.exe -m py_compile app.py
.\.venv\Scripts\python.exe -m pytest -q
```

最低可见结果：两个页面可打开、导航链接有效、至少2项测试通过，控制台没有Traceback。

### 9.3 理解本版代码

在`app.py`中亲自指出：应用在哪里创建、两个URL分别对应哪个函数、函数把哪个模板作为响应；在`base.html`中指出子模板替换的内容块。说不出来时先让AI逐行解释相关20—40行，不继续增加功能。

### 9.4 检查、提交和恢复

```powershell
git status --short
git diff --check
git add .
git commit -m "feat: build AI project static prototype"
git tag -a ai-v0.1 -m "AI project static prototype"
git status --short
```

只有测试通过后提交。失败时把完整命令和Traceback用于第13节调试提示；需要退回时先`git stash push --include-untracked -m "failed attempt after ai-v0.1"`，即可回到最近成功提交。

## 10. 第28课时下半段：从`ai-v0.1`到`ai-v0.2`

### 10.1 本轮目标

把静态列表换成SQLite真实数据，同时只实现公共查询，不提前加入登录和核心业务写操作。

```text
数据模型：本题3个实体中先实现公共主实体；需要关联才能显示详情时，可同时建必要关联
种子数据：至少4条虚构数据，数据库为空时才写入
页面：列表来自数据库；至少一种关键词/状态筛选；详情来自合法ID；不存在ID返回404
测试：总数至少4项，且每项使用临时数据库
```

### 10.2 本轮提示词

```text
当前可运行基线：ai-v0.1。
这是已经确认的模型和路由设计：[粘贴相关表格]
本轮只实现ai-v0.2：SQLite模型、种子数据、数据库列表/筛选/详情和至少4项测试。

要求：
1. 保持ai-v0.1页面和测试通过。
2. 使用Flask-SQLAlchemy，不新增依赖。
3. 使用create_app(test_config=None)，测试数据库必须与手工数据库分离。
4. 数据库为空才写入种子数据，不能每次启动重复插入。
5. 先给文件变更清单，再逐个提供完整新增或修改文件。
6. 给出表数量检查、浏览器验收和pytest命令。
7. 不实现登录和核心业务提交。
```

### 10.3 实际操作和可见结果

按AI确认后的完整文件落地，再执行：

```powershell
.\.venv\Scripts\python.exe -m py_compile app.py models.py
.\.venv\Scripts\python.exe -m pytest -q
```

启动后检查4条以上种子数据、筛选、详情和不存在ID。用一行命令查询实体数量时，命令必须由AI根据你的真实模型类名生成；先读懂导入、应用上下文和查询对象再执行。

若模型字段变化造成旧SQLite结构不一致，停止服务器，把本项目的数据库改名备份，不删除其他目录：

```powershell
Move-Item -LiteralPath .\instance\app.db -Destination .\instance\app-before-v02.db
```

数据库文件名以你的`app.py`真实配置为准。重新启动后验证种子数据。最后提交并标记：

```powershell

git commit -m "feat: add AI project database queries"
git tag -a ai-v0.2 -m "AI project database version"
```

## 11. 第29课时：从`ai-v0.2`到`ai-v0.3`

### 11.1 本轮必须形成一条跨角色闭环

以默认题目为例：

```text
学生登录
→ 选择活动并提交报名
→ 负责人登录并查看待审核记录
→ 通过或有原因地驳回
→ 学生重新登录查看结果
→ 允许时取消自己的报名
```

其他题目替换业务词，但仍要让同一条记录经过两个角色，不能只做“新增、删除、修改、查询”四个孤立按钮。

### 11.2 分两轮要求AI实现

第一轮只做身份和权限：

```text
从ai-v0.2开始，只增加两个角色的演示账号、密码哈希、登录、退出、Session、角色工作台和服务器端权限装饰器。
错误密码不建立会话；未登录访问受保护页面转到登录页；错误角色返回403。
保持现有查询功能和测试通过，总测试先达到6项。
先列变更文件，再提供每个变更文件的完整内容和测试。
```

运行、检查、保存一个普通提交后，第二轮增加业务：

```text
在当前已通过身份测试的代码上，只增加核心记录的提交、本人查看、第二角色处理、合法状态转换和取消。
严格使用我已确认的字段、状态表和验收标准，不增加新角色或新模块。
所有输入在服务端校验；数据归属和角色在路由端检查；非法状态不能保存。
给出完整变更文件、至少2项新增测试和一条浏览器跨角色验收路径，使总测试不少于8项。
```

### 11.3 每一轮都执行同样的门禁

```powershell
.\.venv\Scripts\python.exe -m py_compile app.py models.py
.\.venv\Scripts\python.exe -m pytest -q
git status --short
git diff --check
```

人工验证正确密码、错误密码、未登录、错误角色、正常提交、非法输入、正常处理、重复处理和本人数据边界。全部通过后：

```powershell
git add .
git commit -m "feat: complete AI project role workflow"
git tag -a ai-v0.3 -m "AI project core workflow"
```

### 11.4 操作之后理解AI最容易犯的连接错误

- 页面表单字段名与路由读取名称不一致；
- `url_for()`使用不存在的函数名；
- 数据模型改了字段，模板仍读旧字段；
- 只隐藏按钮，没有服务器端角色检查；
- 修改状态后忘记`db.session.commit()`；
- 测试使用正式数据库，运行后污染手工数据；
- 修复一个角色时删除另一个角色的旧功能。

这些问题通常不靠“提示词写得更有气势”解决，而靠小步修改、读错误信息和每轮回归。

## 12. 第30—31课时：从`ai-v0.3`到`ai-v1.0`

### 12.1 先补测试设计，不先要求“优化整个项目”

根据自己的需求至少形成10项：

| 类别 | 最低数量 | 示例 |
| --- | ---: | --- |
| 正常公共页面/查询 | 2 | 首页200、筛选命中 |
| 正常业务流程 | 2 | 提交成功、处理成功 |
| 异常输入 | 2 | 数量越界、必填内容过短 |
| 身份与权限 | 2 | 未登录重定向、错误角色403 |
| 状态或所有权 | 1 | 不能重复处理或不能查看他人记录 |
| 端到端验收 | 1 | 同一记录经过两个角色并达到终态 |

先写用例编号、前置条件、输入和预期，再让AI把其中适合自动化的用例变成pytest。

### 12.2 测试与质量提示词

```text
当前稳定标签：ai-v0.3。
下面是已确认需求、业务规则和10项测试用例：[粘贴]

请先审查现有代码与测试之间的覆盖关系，然后只完成ai-v1.0质量工作：
1. 把可独立的输入校验提取成小函数并做单元测试。
2. 测试使用tmp_path临时SQLite，不接触instance中的手工数据库。
3. 补足正常、异常、权限、状态/所有权和一条端到端测试，总数不少于10项。
4. 所有POST加入会话防伪令牌，服务器统一验证。
5. 至少提供403和404友好错误页，并保留正确HTTP状态码。
6. 增加VERSION、README、启动和测试脚本。
7. 不新增业务需求，不更换技术栈。

先输出“需求—测试”对应表和变更文件清单；我确认后，再按文件给完整内容、执行命令和预期结果。不要声称你已经运行测试。
```

### 12.3 用真实失败驱动AI调试

执行：

```powershell
.\.venv\Scripts\python.exe -m pytest -x -vv
```

若失败，不发送“有错误，帮我修”。使用固定故障单：

```text
当前成功基线：ai-v0.3，当前目标：ai-v1.0。
我实际执行的命令：[完整命令]
第一个失败测试：[测试完整名称]
完整错误信息：[从FAILED/Traceback开始粘贴，不只发最后一行]
复现步骤与输入：[填写]
预期结果：[填写]
实际结果：[填写]
相关文件当前完整内容：[只粘贴最相关文件]

请：
1. 先区分语法、导入、模板、数据库、业务规则或测试本身的问题。
2. 给出最可能根因和验证方法。
3. 只修改解决该根因所需的最少文件，并输出这些文件的完整内容。
4. 给出先运行单项测试、再运行全量回归的命令。
5. 不删除失败测试，不放宽验收标准来制造通过。
```

AI提出原因后，先用错误行和源码验证推断，再采用修改。

### 12.4 至少关闭一条真实缺陷

在记录册填写：

```text
BUG-AI-01
发现版本：ai-v0.3或ai-v1.0候选版
复现步骤：具体账号、URL、输入和操作
预期结果：来自哪条AI-REQ或业务规则
实际结果：页面、状态码、数据库或Traceback
AI判断：它提出的原因
人工核对：在哪个文件哪段代码确认或否定
修复：实际采用的最小变更
单项回归：命令和结果
全量回归：命令和结果
```

没有遇到自然缺陷时，可在成功提交后临时改错一个边界符号，让测试失败并恢复；必须清楚标注为“教师要求的故意缺陷”，不能伪装成AI真实错误。

### 12.5 形成V1.0候选版

最低检查：

```powershell
.\.venv\Scripts\python.exe -m py_compile app.py models.py
.\.venv\Scripts\python.exe -m pip check
.\.venv\Scripts\python.exe -m pytest -q
git diff --check
git status --short
```

若你的项目没有`models.py`，说明设计没有使用数据库，不符合本实践要求；不能直接删掉命令掩盖问题。

## 15. AI代码必须能够解释到什么程度

答辩时每人现场指出并解释：

1. 一个URL怎样进入Flask路由并渲染模板；
2. 一个数据实体及其与另一个实体的关系；
3. 核心状态在哪一段代码中改变，什么条件阻止非法改变；
4. 一个权限检查为什么不能只写在页面上；
5. 一项自动测试的前置数据、操作、预期断言；
6. 一条AI建议被你拒绝或修改的具体理由。

不要求背出所有代码，但不能用“这部分都是AI写的”代替解释。看不懂时可以要求AI解释，然后用源文件、浏览器和测试验证它的解释。

## 16. 常见问题与课堂救援

### 问题1：AI一次生成20多个文件，回答中还有省略号

停止复制。让AI回到当前版本，只给文件清单；再按一次1—3个文件输出完整内容。省略号不是代码。

### 问题2：AI换成FastAPI、Vue、MySQL或要求Node.js

拒绝该方案，重新发送第5节工作约定和固定依赖。不要为了迁就回答临时安装另一套环境。

### 问题3：改了一个文件后出现连锁错误

先运行`pytest -x -vv`只看第一个失败；核对路由函数名、模板名、表单字段和模型字段。使用第12.3节故障单，不把十几个错误一次扔给AI。

### 问题4：数据库报缺列或旧表结构不一致

确认修改是否符合定版设计。开发期确需重建时，只改名备份当前项目`instance`中的准确数据库文件，再启动生成；不得删除整个项目或其他课程数据库。

### 问题5：AI为了通过测试删除断言或放宽规则

拒绝修改。预期来自已确认需求；除非需求本身经过教师批准变更，否则修复实现，不修改正确的测试来迁就错误结果。

### 问题6：页面能用，但测试污染手工数据库

要求AI使用`create_app(test_config)`、pytest fixture和`tmp_path`。执行测试前后比较手工数据库记录数；测试不应改变它。

### 问题7：当前尝试已经混乱，不知道改了什么

先保存错误和AI对话摘要，然后：

```powershell
git diff --stat
git stash push --include-untracked -m "failed AI attempt for review"
git status --short
git log --oneline --decorate -5
```

回到最近成功版本后，把任务缩小为一个路由或一个测试再提问。stash可由教师后续检查。

### 问题8：个别学生进度明显落后

依次缩减：停止自选题并改用默认题目A；停止增加AI-REQ-07/08；只完成两个角色、一条主线和10项测试。不得取消测试、权限和Git版本这些核心学习目标。

## 19. 综合练习

### 练习1：识别需求越界

AI为社团活动系统主动增加支付、短信通知、人脸签到和推荐算法。逐项判断是否属于已定范围，并写出拒绝提示，要求它回到当前版本。

本练习不修改源码，无需恢复。

### 练习2：把模糊要求变成测试

把“报名人数不能太多”改写为包含容量字段、边界值、错误结果和是否保存数据的验收标准，再设计容量为40时的四个边界输入。

本练习不修改源码，无需恢复。

### 练习3：验证AI解释

任选AI对一段路由的解释，分别在源码中定位输入、权限、数据库写入和返回值；若解释与源码不一致，记录一处并要求AI依据当前完整文件重新解释。

本练习只产生审查记录，无需恢复。

### 练习4：发现测试覆盖空白

查看自己的10项测试，找出一个“页面可以正常点，但自动测试没有证明”的行为，补写用例；有余力者再把它自动化。

修改后运行全量测试；不通过时用Git diff定位，不能删除原有测试。

### 练习5：比较两种开发方式

从速度、需求理解、错误类型、代码理解、测试责任和可恢复性六方面比较前24课时的手工引导开发与本次AI辅助开发，每项必须引用一个自己的真实例子。

本练习不修改源码，无需恢复。
