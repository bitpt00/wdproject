# T04 半自动教学平台32课时角色分工与实施矩阵

## 1. 文档定位

本文件把现有32课时课程转换为“教师专注讲解、学生亲手体验、平台保证走通”的课堂实施规格。它同时回答五个问题：

1. 每一课时教师重点讲什么。
2. 每一课时学生必须思考什么。
3. 每一课时学生必须亲手完成什么操作。
4. 哪些机械工作可以由平台代劳。
5. 怎样用手工测试、自动测试和个人解释证明学生真正理解。

本文件中的“平台”是计划建设的半自动教学实验平台，不表示这些功能目前已经全部实现。在平台完成之前，T01授课脚本、S00—S13讲义、版本终点核对包和T03救援指南仍是可执行的人工替代路径。

## 2. 课程运行模式

### 2.1 一句话定位

> 平台消除机械性困难和偶然性错误，学生完成观察、判断、操作、测试、解释和验收，教师专注于过程、知识与真实项目经验。

### 2.2 三方职责边界

| 教学活动 | 教师负责 | 学生必须负责 | 平台可以负责 |
| --- | --- | --- | --- |
| 建立情境 | 说明当前业务问题、版本位置和真实项目背景 | 观察当前版本并用自己的话描述问题 | 打开准确起点、恢复演示数据 |
| 知识讲解 | 讲当前任务所需的核心概念、因果关系和经验 | 记录关键概念，并把概念对应到当前系统 | 展示结构图、知识卡和当前源码位置 |
| 作出决定 | 提问、比较方案、说明取舍依据 | 选择范围、需求、实体、状态、权限或测试方法 | 提供受控选项、完整性检查和即时反馈 |
| 代码落地 | 解释本轮修改解决什么问题 | 先预测修改位置，再触发操作、观察差异并解释 | 从已验证检查点应用完整文件，保存快照 |
| 运行系统 | 示范一次关键操作及观察方法 | 亲自启动、登录、查询、提交、审批、取消或管理 | 检查端口和环境，启动服务，记录操作事件 |
| 测试 | 讲测试目标、方法和真实缺陷经验 | 先写预期，再执行正常、异常和权限场景 | 提供用例模板，运行自动测试，解释失败报告 |
| 排错 | 讲诊断顺序，不直接替学生点击完成 | 观察现象、判断类别、尝试第一层处理 | 分级提示，最后才提供精确恢复 |
| 版本与提交 | 讲基线、差异、标签和发布的意义 | 输入版本说明、查看差异、确认建立基线 | 防止错目录操作，执行安全命令并核验结果 |
| 课堂评价 | 抽查原因、影响、测试和经验 | 提交本人运行结果和解释 | 汇总进度、测试、提示使用和学习证据 |

### 2.3 平台明确不能代替的事情

- 不能替学生判断当前版本解决了什么问题。
- 不能替学生选择需求、业务规则、实体关系和状态变化。
- 不能在学生没有预测结果时直接显示答案。
- 不能替学生完成浏览器中的核心业务流程。
- 不能在学生尚未写预期结果时直接运行全部测试。
- 不能把自动测试通过等同于学生已经理解。
- 不能发生失败后立即覆盖正确答案，必须先让学生观察和判断。
- 不能用一个“升级到下一版”按钮静默替换全部文件。

## 3. 每个教学任务的固定学习闭环

平台中的每个任务都按以下状态推进：

| 状态 | 学生必须完成的事情 | 平台判定依据 |
| --- | --- | --- |
| ① 起点确认 | 启动或检查规定版本，指出一个当前现象 | 版本、文件、数据库和起点测试正确 |
| ② 问题识别 | 说明本轮要解决的问题及其影响 | 回答包含使用者、现象和影响，不把技术方案当问题 |
| ③ 操作预测 | 预测涉及的系统层次、文件、数据或状态 | 提交选择或简短说明后才开放执行 |
| ④ 亲手操作 | 逐步触发修改、启动系统并完成规定业务操作 | 平台记录真实按钮、页面、账号、业务编号和状态 |
| ⑤ 变化解释 | 对照前后版本说明做了什么、为什么做和产生什么效果 | 完成“动作—位置—意义—结果”四项说明 |
| ⑥ 测试设计 | 写清前置、输入、步骤和预期，至少包含正常与异常 | 用例字段完整，预期是可观察结果 |
| ⑦ 测试执行 | 亲自执行手工用例，再运行规定自动测试 | 实际结果、结论和自动测试数可核验 |
| ⑧ 故障处理 | 失败时先分类、查看证据，再选择处理方法 | 保存失败现象、第一次判断、处理和回归结果 |
| ⑨ 版本验收 | 对照需求和终点标准作出通过或不通过判断 | 功能、测试、解释、版本和记录全部满足门禁 |

任何任务如果只有“代码已替换”或“自动测试通过”，状态最多只能到第④步，不能判定为完成。

## 4. 每课时统一节奏

除生命周期分析和最终展示课外，每个45分钟课时优先采用下面的节奏。教师的连续讲授一般控制在15分钟以内，把更多时间留给学生真实操作和解释。

| 时间 | 教师活动 | 学生活动 | 平台活动 |
| ---: | --- | --- | --- |
| 0—5分钟 | 显示当前起点、终点和一个真实问题 | 启动规定起点，确认当前现象 | 检查版本、环境、数据库和起点测试 |
| 5—15分钟 | 讲本轮核心知识、过程关系和一个项目经验 | 记录概念，回答问题，预测修改位置与结果 | 展示知识卡、结构图和预测题，不开放答案 |
| 15—20分钟 | 演示第一个关键动作，解释为什么这样做 | 观察并提交自己的操作计划 | 准备快照，检查学生是否满足操作条件 |
| 20—33分钟 | 巡视，针对共性问题补充讲解 | 逐步触发修改，运行系统，完成业务操作 | 应用准确步骤、显示差异、记录操作、分级提示 |
| 33—40分钟 | 引导测试，追问预期来自哪条需求或规则 | 设计并执行手工测试，随后运行自动测试 | 检查用例字段，运行测试，显示业务化结果 |
| 40—45分钟 | 抽查两到四人，联系真实项目总结 | 解释本轮变化，提交证据，判断是否验收 | 执行硬门禁并生成本课记录 |

## 8. 教师授课界面要求

教师界面每课时只保留六个区域，使教师可以把注意力放在讲解而不是技术救火上：

1. **本课位置**：生命周期位置、当前版本、起点、终点和剩余时间。
2. **讲解提纲**：最多3个核心概念、1张当前项目图、1条真实项目经验。
3. **演示入口**：一键打开准确版本和干净演示数据，但每个操作仍由教师现场完成。
4. **学生任务**：本课必须思考、必须操作、必须测试、必须解释的清单。
5. **班级状态**：未开始、进行中、需帮助、待解释、已达标；若无课堂网络，此项可由学生本机状态页替代。
6. **课末抽查**：平台随机给出2—4个问题，优先抽问原因、影响、测试和异常，不抽背语法。

教师不需要在授课界面中逐行检查学生代码。发生个别问题时，先由P11按T03规则处理；只有同一问题集中出现时，教师才暂停全班统一讲解。

## 9. 学生实验界面要求

学生界面中的每一步都必须同时看见以下内容：

| 区域 | 必须显示的内容 |
| --- | --- |
| 当前任务 | 从什么起点开始，只解决什么问题，到什么终点结束 |
| 操作前思考 | 修改位置、预期现象、业务规则或测试预期 |
| 本人操作 | 一个明确动作及操作对象，不连续堆放十几个按钮 |
| 平台实际动作 | 新增/修改了哪些文件、数据或配置，执行了什么命令 |
| 可见结果 | 应在哪个页面、数据库、终端或测试报告观察什么 |
| 含义解释 | 这一步为什么存在，在架构中处于哪里，产生什么业务影响 |
| 测试与问题 | 正常、异常、权限或状态场景，以及可能出现的问题 |
| 恢复入口 | 当前步骤恢复和当前版本恢复，并说明恢复会影响什么 |
| 完成证据 | 学生答案、实际操作、测试结果、版本号和时间 |

平台按钮状态至少区分：未开始、已操作待观察、已观察待解释、已解释待测试、测试失败待处理、已验收。不得只有“完成/未完成”两种状态。

### 10.1 必须保留的教学问题

- 错误密码和未登录访问。
- 错误角色直接访问受保护地址。
- 人数边界、非数字和缺少必填内容。
- 查询不存在的实验室。
- 查看他人的预约。
- 对已经处理的预约重复审批。
- 缺少请求防伪令牌。
- 有有效预约时停用实验室。
- 自动测试预期和实际不一致。

这些问题由学生亲自触发、观察、解释和记录，平台不能提前拦截到完全看不见。

### 10.2 平台应优先消除的偶然问题

- Python路径、依赖或虚拟环境损坏。
- 中文路径、工作目录和脚本双击无输出。
- 端口占用和浏览器没有自动打开。
- 大文件复制漏行、缩进和编码错误。
- 旧数据库结构与当前版本不匹配。
- 临时测试、教学缺陷或练习修改没有恢复。

平台先显示真实原因和处理动作，再执行修复，使学生知道发生了什么，但不让这些问题吞噬课堂时间。

### 10.3 四级救援

| 级别 | 平台行为 | 学生仍需完成的事情 |
| --- | --- | --- |
| 1 观察提示 | 指出应查看的页面、状态码、日志或数据 | 描述实际现象，不猜答案 |
| 2 检查方向 | 提示检查账号、状态、输入、路径或版本 | 判断问题类别并选择下一项检查 |
| 3 局部恢复 | 恢复当前微步骤涉及的准确文件或数据库 | 重新操作、测试并解释刚才失败原因 |
| 4 版本恢复 | 从冻结终点包恢复到最近成功基线 | 完成规定业务操作、测试和版本记录后才能继续 |

使用恢复不等于学习任务完成。恢复后仍必须经过变化解释、手工测试、自动测试和课末抽查。

## 11. 平台验收标准

半自动教学平台只有同时满足以下条件，才算达到本课程使用标准：

- [ ] 32个课时均有准确起点、终点、教师讲解、学生思考、学生操作和测试证据。
- [ ] 每个实操课至少有1项学生真实操作、1项原因解释和1项可观察结果。
- [ ] 每次正式版本推进都分成若干可恢复微步骤，不存在静默整版替换。
- [ ] 每个微步骤应用的完整文件来自已验证检查点，最终与对应Git标签一致。
- [ ] V0.1—V1.0分别达到6、10、14、18、22、28、34项测试。
- [ ] 自动测试之前，学生已经填写至少一项本轮手工测试的预期结果。
- [ ] 学生必须亲自完成角色切换、业务流转、异常操作和最终端到端验收。
- [ ] 自动测试通过不能单独解锁下一阶段，仍需解释和记录通过。
- [ ] 教学故障可以准确恢复，恢复不会修改其他版本、教师答案或未知目录。
- [ ] 教师可以从一个界面打开讲解提纲、演示入口、学生任务和课末抽查。
- [ ] 学生个人报告能够追踪到本人版本、操作、测试、缺陷和验收结果。
- [ ] 平台不要求学生安装或掌握课程范围外的复杂开发工具。
- [ ] 没有课堂网络时，核心教学、运行、测试、恢复和报告仍可完成。

## 12. 建设顺序

平台建设应按“先验证课堂闭环，再扩展版本”的顺序推进：

| 阶段 | 建设范围 | 完成判据 |
| --- | --- | --- |
| 第1阶段 | 实现S0→V0.1 | 学生从3个起点文件出发，完成项目结构、最小Flask链路、静态原型、手工验收、6项自动测试、解释、恢复和V0.1基线 |
| 第2阶段 | 实现V0.1→V0.2并连接首个完整原型 | 学生能从S0连续走到V0.2，完成模型设计、数据库观察、查询、手工测试、10项自动测试和恢复 |
| 第3阶段 | 加入V0.3和V0.4 | 登录、授权、预约、所有权、边界和冲突能够真实操作并记录 |
| 第4阶段 | 加入V0.5、V0.6和V1.0 | 审批、状态历史、缺陷闭环、34项测试、端到端和发布全部走通 |
| 第5阶段 | 加入第1—7课时分析设计 | 问题、可行性、需求、UML能够与版本和测试双向追踪 |
| 第6阶段 | 加入AI独立实践和教师进度页 | AI项目仍按生命周期、版本和证据评价，教师不需要逐机处理常规故障 |

第1阶段完成后必须找2—5名目标专业学生试用。只有在无人指导的情况下，他们能从S0得到V0.1，并且仍能说明“做了什么、为什么做、怎样测试”，才进入V0.1→V0.2建设；仅仅能够点到V0.1不算试用通过。

## 13. 与现有材料的对应关系

| 现有材料 | 在平台中的作用 |
| --- | --- |
| 课程总矩阵 | 确定32课时、生命周期和版本边界 |
| S00—S05 | 转换为课程地图、知识卡、分析表和设计任务 |
| S06—S12 | 转换为七次版本推进的讲解、操作、观察、测试和恢复任务 |
| S13 | 转换为AI独立项目的范围、版本、测试和人工审查流程 |
| A06—A12 | 提供正式终点完整源码，不直接要求学生手抄 |
| 七个版本终点包 | 提供恢复、文件核对和最终验收基线 |
| T01 | 提供教师分钟级讲解与演示脚本 |
| T02 | 提供平台门禁、教师抽查和评分依据 |
