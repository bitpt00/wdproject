# T01 32课时教学实施与演示脚本

## 1. 这份脚本怎样使用

本课程面向非计算机专业学生，连续4天、每天8课时、每课时45分钟，在学生自带笔记本的机房实施。每位学生独立完成一套项目，不分组、不设置“组长写代码、其他人观看”的任务。

教师上课时同时打开三类材料：

- [课程总矩阵与文档索引](../00_课程总矩阵与文档索引.md)：控制全课程边界和课时位置；
- 对应的S00—S13学生讲义：显示完整操作、代码来源、预期结果和恢复方法；
- 本脚本：控制教师讲解、现场演示、个人任务和课末门禁。

本脚本不替代完整代码附录。凡是要求学生创建或覆盖源码，教师必须指向该版本的A06—A12附录或版本终点核对包，不从投影画面手抄零散片段。

## 2. 开课前教师必须准备的环境

### 2.1 文件和软件

教师机至少准备：

```text
campus-lab-development完整课程目录
├─ 教学文档
├─ 教学资源
├─ 七个Git标签dev-v0.1—dev-v1.0
└─ 可用的.venv

Python 3.11.x
Git
VS Code或其他文本编辑器
Chrome或Edge
能投影的PowerShell窗口
```

第四天还要提前确认学生能够访问学校允许使用的AI工具。课程不绑定某一品牌；若外网不稳定，应在开课前确定校内可用替代入口，不能到第25课时才测试账号。

### 2.2 一次性预检

在课程项目根目录执行：

```powershell
py -3.11 --version
git --version
.\.venv\Scripts\python.exe -m pip check
git tag --list
.\.venv\Scripts\python.exe -m pytest -q
```

教师预期看到：Python 3.11.x、Git可用、依赖无冲突、7个开发标签齐全、最终34项测试通过。

再逐项确认：

| 检查项 | 通过标准 |
| --- | --- |
| S0起点包 | 3个文件齐全，`.gitignore`可见 |
| 七个终点包 | dev-v0.1—dev-v1.0目录齐全 |
| 完整代码附录 | A06—A12均可打开，中文和代码围栏正常 |
| 批处理脚本 | 初始化、启动、测试可以在含中文的路径中执行 |
| 最终系统 | 首页、三个账号、`/version`和`/health`可用 |
| 学生记录册 | 能复制并改名为“学号_姓名_学生项目开发记录册.md” |
| AI起点包 | 3个文件齐全，依赖为Flask、Flask-SQLAlchemy、pytest |

### 2.3 教师演示副本

不要直接在冻结终点包中边讲边改。课前为教师创建一个可丢弃的演示副本和一个干净验收数据库；冻结包只读保留，用于随时恢复。

演示每个版本时遵守：

```text
先停止上一个服务器
→ 明确投影当前版本和测试数
→ 再启动当前演示副本
→ 演示后保留记录或重新复制，不改冻结答案
```

第一天课前至少完整走通一次最终主线：学生提交、教师通过、学生取消、管理员停用和恢复。

## 3. 全课程统一的45分钟组织方式

除特别说明外，每课时使用下面节奏：

| 时间 | 教师行为 | 学生行为 |
| ---: | --- | --- |
| 0—5分钟 | 显示本节起点、终点和一项可见问题 | 打开指定目录，报告起点检查结果 |
| 5—15分钟 | 只讲本节解决问题所需的核心原理 | 在记录册填概念、规则或预测结果 |
| 15—28分钟 | 投影完成第一个关键操作，边做边解释 | 跟做同一步并得到相同可见结果 |
| 28—40分钟 | 发布剩余个人任务，巡查真实屏幕 | 独立完成、运行、测试和记录 |
| 40—45分钟 | 做课末门禁和一到两个口头抽查 | 出示命令结果、页面或表格，保存当前状态 |

教师每次发布操作任务必须说清五句话：

```text
现在从哪个起点开始
本轮只解决什么问题
要操作哪个完整文件或哪张表
成功后屏幕上应看到什么
失败时先停在哪里，不允许继续做什么
```

## 4. 一人一项目的课堂检查机制

### 4.1 不用分组也能快速检查

每课时使用三层证据：

1. **全员同时举证**：学生把指定终端结果或页面停在屏幕上，教师巡视一圈。
2. **随机口头抽查**：随机点2—4人解释一个结果从哪里产生，不能只回答“成功了”。
3. **记录册留痕**：每人填写自己的版本、提交号、实际测试数、失败原因或分析表。

不能把邻座电脑上的结果算作自己的证据，也不能提交统一截图。

### 4.2 课末三种状态

| 状态 | 判定 | 下一步 |
| --- | --- | --- |
| A 已达标 | 本节硬门禁全部通过 | 正常进入下一课时 |
| B 可跟进 | 核心结果通过，记录或练习未完成 | 课间补记录，不影响下一版本 |
| C 未达标 | 起点错误、程序不能运行或规定测试失败 | 立即使用本节救援路径，不能带错进入下一课 |

救援不是降低要求。学生可以用终点包恢复代码，但仍要运行、测试并解释本节核心关系。

### 4.3 每版统一硬门禁

```text
起点测试通过
→ 按讲义完成当前变化
→ 浏览器关键场景通过
→ 自动测试达到规定数量
→ 与终点文件一致
→ Git提交和标签成功
→ 工作区干净
```

任一步失败都不建立当前标签。

## 5. 第一天：认识软件全过程并做出V0.1

### 第1课时：先看终点，再理解四天要做什么

**本节目标**：学生能说出最终系统、三类角色、核心流程、七个版本和最终个人成果。使用S00。

**0—5分钟，教师开场**

投影最终首页，不先展示代码。教师可以直接说：

> 这四天不是听32节软件工程名词，也不是要求大家凭空写出大程序。我们会先看一个完整系统，再沿着七个可运行版本，从问题、需求、设计走到测试和发布；最后每个人用AI再独立做一个同规模系统。

在白板写：`问题→需求→设计→版本→测试→发布→AI再实践`。

**5—18分钟，演示最终产品**

按同一条数据演示：

1. 访客查看首页、实验室列表和详情。
2. 学生`20260001`登录并提交预约。
3. 审批教师`T1001`登录并通过。
4. 学生查看结果。
5. 管理员`A001`查看管理入口。
6. 打开`/version`和`/health`。

只讲“谁做什么、数据怎样变”，不解释装饰器、ORM和CSRF。

**18—30分钟，展示七个版本**

用S00版本表逐个展示截图或短暂打开页面。每版只问一个问题：“它比上一版多解决了什么？”明确0.x是开发基线，1.0是本课程第一套完整范围。

**30—40分钟，学生独立体验**

学生打开最终系统，分别记录三类角色可见入口和一条状态变化。不能两人共用一台电脑操作。

**40—45分钟，门禁**

随机抽查：一个学生说最终产品，另一个说生命周期，第三个说版本的作用。全员在记录册封面填姓名、学号和课程成果。

达标证据：能用自己的话说出“三种角色＋一条主线＋七次升级”。未达标者重新走S00第5节观察路线。

### 第2课时：环境、工具和本地服务器

**本节目标**：每台电脑建立独立`.venv`，能够区分Python、库、编辑器、终端、浏览器和服务器。使用S01。

**0—8分钟，讲解六种工具的职责**

投影一条链：

```text
编辑器保存文件
→ Python解释执行
→ Flask提供本地服务器
→ 浏览器发请求并显示响应
→ SQLite保存数据
→ Git保存代码历史
```

强调浏览器不是运行Python，VS Code也不是Python解释器。

**8—18分钟，教师演示环境检查**

依次运行`py -3.11 --version`、创建虚拟环境、使用虚拟环境Python、安装锁定依赖和`pip check`。故意展示一次在错误目录执行命令的现象，再用`Get-Location`和`Get-ChildItem -Force`纠正。

**18—37分钟，学生独立完成S01**

教师巡视只看三项：命令提示符当前路径、Python实际路径、`.venv`是否位于项目内。不要代学生点击完成全部步骤。

**37—45分钟，门禁**

全员停在S01环境检查输出。随机问：“删除`.venv`会不会删除项目源码？”“为什么不装到全局？”

达标证据：Python 3.11.x、规定依赖版本、`pip check`无冲突。失败者使用S01常见问题逐项排查；不能直接借用教师`.venv`。

### 第3课时：Git和第一个可恢复起点

**本节目标**：建立课程贯穿项目的S0基线（不是第四天的`ai-s0`），理解工作区、暂存区、提交和标签。使用S02。

**0—10分钟，先演示为什么需要Git**

在演示文件加一行，再运行`git diff`，然后恢复。教师板书：

```text
工作区：正在改
暂存区：准备提交
提交：有说明的历史快照
标签：给重要提交取固定名字
```

不要在本课讲分支合并、远程冲突和复杂命令。

**10—22分钟，教师演示S0提交**

复制S0三个文件，执行`git init -b main`、`git status`、`git add`、`git commit`和`git log`。投影`.gitignore`，说明为什么`.venv`不提交。

**22—39分钟，学生独立建立仓库**

教师重点检查是否在正确项目目录初始化；发现上级目录出现`.git`时立即停下，由T03救援，不能继续提交整个磁盘目录。

**39—45分钟，门禁**

学生停在`git status --short`和`git ls-files`。规定结果：工作区干净，跟踪文件恰为3个。随机让学生指出自己的提交号。

### 第4课时：软件生命周期和问题定义

**本节目标**：从“想做功能”退回到“谁遇到什么问题”，确定项目目标、范围和约束。使用S03前半。

**0—8分钟，建立生命周期全景**

画出问题定义、可行性、需求、设计、实现、测试、发布和维护。强调阶段会回看，但每阶段回答的问题不同。

**8—18分钟，演示错误问题定义**

对比：

```text
错误：做一个Flask预约系统。
正确：实验室预约信息分散，学生难以确认空闲时段，教师难以统一审批和追踪状态。
```

前者是方案，后者才是需要解决的现象。

**18—36分钟，学生填写记录册**

完成当前业务3—6步、两个问题证据、一句话定义、三个可检查目标、范围内/范围外。教师对每人只追问：“你写的是问题，还是已经跳到功能？”

**36—45分钟，门禁**

随机展示两份匿名或经同意的定义，全班判断目标是否可检查。达标证据：至少1个具体使用者、2个问题、4项范围外。

### 第5课时：可行性、技术选择和风险

**本节目标**：用证据选择Flask+SQLite，并识别环境、进度、数据和AI使用风险。使用S03后半。

**0—12分钟，讲四类可行性**

技术回答“做不做得出”，经济回答“资源是否承担”，操作回答“使用者能否使用”，时间回答“规定课时能否完成”。风险回答“什么事件可能让计划失败以及怎么办”。

**12—23分钟，比较两条技术路线**

投影Flask+Jinja2+SQLite与Spring Boot+Vue+MySQL表。不要评价哪个技术“高级”，只结合4天、非计算机专业、个人笔记本和无外部部署判断适配度。

**23—38分钟，学生形成结论**

每人完成四类可行性、至少3条风险和“有条件可行”结论。风险必须是未来不确定事件，不能写成已经发生的普通问题。

**38—45分钟，门禁**

抽查一条高风险及其预防、发生后的应对。达标证据：选择技术路线的依据至少同时包含时间、安装量和教学目标。

### 第6课时：从愿望变成可验收需求

**本节目标**：理解功能/非功能需求、角色、用例、业务规则、优先级和验收标准；定版REQ-01—REQ-10。使用S04。

**0—12分钟，教师讲三组区别**

```text
需求：系统必须提供什么结果
设计：准备怎样组织程序

功能需求：用户能完成什么
非功能需求：系统必须达到什么质量

需求描述：要做什么
验收标准：怎样判断完成
```

**12—22分钟，现场改写一条需求**

把“系统要方便预约”改为REQ-04，逐项指出角色、动作、输入、保存结果和冲突规则。再展示一个不可测试词，让学生改写。

**22—37分钟，学生完成基线**

按S04抄写并理解10条需求和8条规则，完成角色—用例、核心用例和需求—版本—测试追踪。任务是解释和核对，不要求非计算机专业学生从空白发明整套需求。

**37—45分钟，门禁**

教师随机说一个页面或规则，学生回答需求编号和验收证据。规定结果：REQ-01—REQ-10编号不缺失、不重复，每项有首次版本。

### 第7课时：系统设计和UML是开发前的地图

**本节目标**：把需求映射到架构、模块、页面、实体、权限和UML。使用S05。

**0—10分钟，先讲每张图回答的问题**

用例图回答谁用什么；类图回答保存什么及怎样关联；活动图回答业务步骤；状态图回答一个对象怎样变化；顺序图回答一次请求中对象怎样协作。

**10—23分钟，教师沿一条预约解释全部设计**

从浏览器请求到Flask路由，再到模型/SQLite和Jinja2响应；随后在类图找User、Lab、TimeSlot、Booking，在状态图找PENDING。特别指出请求先到Flask，不是浏览器直接访问Jinja2。

**23—38分钟，学生独立补全设计**

每人完成模块表、页面入口、五个实体、角色权限和关键图的观察问题。至少选择一张图，逐项映射到REQ编号。

**38—45分钟，门禁**

随机问：“按钮藏起来等于授权吗？”“当前状态和历史记录分别回答什么？”达标证据：能从REQ-04找到预约页面、路由、三个相关实体和PENDING状态。

### 第8课时：S0到V0.1的第一个可运行页面

**本节目标**：理解HTTP请求、Flask路由、Jinja2模板和静态文件，做出最小运行骨架。使用S06前半。

**0—8分钟，明确固定起终点**

投影S0三个文件和V0.1十三个文件，强调本节只到“最小首页”，下节再补完整原型。

**8—18分钟，教师现场创建最小应用**

严格按S06先创建目录、`app.py`和一个模板；每创建一个文件就投影路径。运行后解释终端服务器、浏览器请求和200响应。

**18—36分钟，学生跟做**

学生从S0独立创建最小文件，运行`py_compile`和首页。教师先检查路径、缩进、模板目录，再看复杂错误。

**36—45分钟，门禁**

达标证据：`http://127.0.0.1:5000/`可打开，终端无Traceback；学生能指出URL、路由函数和模板三者。未达标者停在最小应用，不提前复制完整V0.1。

## 6. 第二天：数据库、登录和学生预约

### 第9课时：完成并冻结V0.1静态原型

**起点/终点**：昨天可运行最小首页→13文件`dev-v0.1`。使用S06后半和A06。

**0—8分钟**：复查首页，讲模板继承解决的重复问题。投影`base.html`中的公共结构和子模板内容块。

**8—23分钟**：教师按S06演示整体复制剩余模板、CSS和测试，提醒CSS使用准确资源，不在投影中手抄551行。

**23—34分钟**：学生完成首页、实验室列表和静态预约表单，逐项执行5个手工场景。

**34—40分钟**：运行6项测试和13文件核对。解释自动测试只是重复验证当前V0.1范围，不代表数据库或登录已经存在。

**40—45分钟**：提交并标记`dev-v0.1`。门禁为`6 passed`、13行PASS、工作区干净、标签可查。C状态学生用V0.1终点包恢复后再次运行。

### 第10课时：V0.1到V0.2的数据模型和SQLite

**起点/阶段终点**：`dev-v0.1`→数据库自动生成并含4间实验室。使用S07前半。

**0—10分钟**：用“重启后静态列表不能变化”引出持久化。讲表、行、列、主键、外键和ORM各一句定义。

**10—23分钟**：教师整体复制锁定依赖、`models.py`和阶段`app.py`，启动并观察`instance`数据库。演示数据库为空才播种，不把数据库文件提交Git。

**23—37分钟**：学生完成模型和数据库检查命令，记录4间实验室名称、容量与状态。

**37—45分钟**：门禁为数据库存在、查询返回4、代码语法通过。抽查：“Python类、数据库表、页面卡片分别是哪一层？”

### 第11课时：完成V0.2查询、筛选和详情

**起点/终点**：数据库阶段结果→15文件`dev-v0.2`。使用S07后半和A07。

**0—9分钟**：讲查询条件、GET查询参数和404。用`?keyword=人工智能&status=可预约`拆解URL。

**9—22分钟**：教师演示列表查询、关键词筛选、状态筛选、合法详情和`/labs/999`。

**22—34分钟**：学生复制完整模板与测试，完成7项手工验收；记录“空结果”和“不存在详情”的区别。

**34—40分钟**：运行10项测试和15文件核对。

教师收集或抽查：环境结果、S0提交、问题/可行性/需求/设计记录、V0.1最小首页。提醒第二天起点必须能运行，不能只带截图。

### 第二天结束

每人至少拥有`dev-v0.1`、`dev-v0.2`、`dev-v0.3`和尚未冻结的V0.4业务代码。进度落后者使用V0.3终点包作为第14课时固定起点，不能跳过权限理解。

### 第三天结束

手工项目必须有七个标签、34项测试和V1.0验收。第四天新建独立项目，不再继续给手工项目堆功能。

### 第四天结束

收取两个层次成果：手工贯穿项目证明学生理解统一过程；AI个人项目证明学生能自己约束需求、分步生成、验证和解释。

## 10. 教师每日结束检查单

## 11. 教师讲授边界

本课程要反复讲清并检查的是：问题、范围、需求、设计、增量版本、数据、角色、状态、测试、缺陷、验收、发布和AI验证责任。

以下内容只在案例出现时解释到“能操作、能判断”的程度，不扩展成专业程序设计课程：Python高级语法、CSS细节、SQL优化、分布式架构、云原生部署、复杂Git分支策略和渗透测试。

教师判断一段内容是否值得讲，可问：

> 它能否帮助学生完成当前版本、理解一个核心软件工程概念，或验证一个真实结果？

若三者都不能，就不占用当前45分钟。
