# T02 版本验收、评分标准与参考结果

## 1. 评价目标

本课程不把“能否独立手写大量Python代码”作为非计算机专业学生的主要考核。允许学生按讲义复制完整文件，也允许第四天使用AI生成代码；评分依据是学生是否真实完成并理解以下过程：

```text
从问题和范围形成可验收需求
→ 用设计连接页面、数据、权限和状态
→ 从固定起点逐版得到可运行终点
→ 用手工和自动测试验证正常及异常结果
→ 记录并关闭真实缺陷
→ 用需求追踪和Git标签形成发布证据
→ 审核AI输出，而不是把AI回答当成运行结果
```

评价坚持四条原则：

1. 每人独立操作和提交，不使用小组总成绩。
2. 真实运行结果优先于截图数量和文档篇幅。
3. 核心流程、权限、状态和测试优先于界面装饰和功能数量。
4. 使用终点包救援不等于零分；学生必须记录原因、重新运行并能解释关键结果。

### 4.2 单版本怎样给分

每版先按该版分值折算下面四类证据：

| 证据 | 占该版比例 | 满分判定 |
| --- | ---: | --- |
| 核心功能实际可操作 | 40% | 按本版验收场景得到预期页面、状态或数据库结果 |
| 自动测试实际结果 | 25% | 使用个人环境运行，达到该版规定数量，失败项为0 |
| Git版本证据 | 20% | 有独立提交和准确标签，能显示起点/终点差异，工作区状态已记录 |
| 本人理解与版本记录 | 15% | 能说明本版解决的问题、一个关键文件/规则和实际失败或检查结果 |

示例：V0.4满分7分。一名学生功能闭环完整、18项测试通过、标签存在，但不能解释所有权检查，建议给约6—6.5分，而不是因代码复制直接判0分。

### 4.3 不应重复扣分

- 同一个遗漏导致页面失败和测试失败时，可以在该版本功能与测试两项分别反映，但不要又在A部分重复重罚。
- 学生按教师救援流程覆盖终点后，只要测试、记录和解释合格，仍可获得大部分版本分；可在“个人完成过程”酌减该版最多15%。
- Git提交信息文字不漂亮但能准确定位版本，不扣功能分。
- CSS与参考版略有视觉差异但不影响页面和规则，不按文件精确一致扣核心分；若课程要求固定起终点，则在版本证据中反映。

## 5. 七个版本的教师快速验收

### 5.1 每版2—4分钟抽查法

要求学生在自己的项目根目录依次执行：

```powershell
git status --short
git tag --list
git log --oneline --decorate -8
git show dev-v1.0:VERSION
.\.venv\Scripts\python.exe -m pytest -q
```

教师同时完成：

1. 看当前目录确实是该生项目，不是课程终点包。
2. 看7个标签及提交是否能形成先后历史。
3. 看最终34项测试是刚刚运行，不是粘贴文字。
4. 随机选一个版本，让学生演示核心结果或解释差异。
5. 在记录册核对实际提交号，而不是只看标签名称。

标签存在不代表内容正确。需要抽查旧版本时，优先使用只读命令，不直接切换学生当前工作区：

```powershell
git show dev-v0.4:VERSION
git diff --stat dev-v0.3 dev-v0.4
git show dev-v0.4:app.py | Select-String -Pattern "def reserve|def cancel_booking"
```

### 5.2 各版一个最快功能抽查

| 版本 | 最快抽查 | 正确结果 |
| --- | --- | --- |
| V0.1 | 打开首页、列表、静态预约页 | 三页可用，无数据库或登录要求 |
| V0.2 | 搜索“人工智能”，再访问`/labs/999` | 命中对应实验室；不存在编号404 |
| V0.3 | 错误密码登录；教师账号开学生预约页 | 不建立会话；错误角色403 |
| V0.4 | 两名学生访问同一预约；本人取消 | 他人403；本人取消后时段恢复 |
| V0.5 | 驳回原因“无”；对已处理申请重复审批 | 均返回400，状态不被错误改变 |
| V0.6 | 删除登录页令牌后提交；打开不存在详情 | 400防伪说明页；404说明页 |
| V1.0 | 有有效预约时管理员停用；打开`/health` | 停用返回400；健康JSON为V1.0和数据库ok |

旧版本功能抽查可由记录、测试和Git只读证据完成，不要求课堂评分时在同一目录来回切换七次。

| 评分项 | 分值 | 满分标准 | 部分得分规则 |

### 7.2 不按题目难度加分

默认社团活动题完整达到标准，可以获得满分。自选复杂商城、聊天或推荐系统不会因代码多自动加分；若范围失控导致权限、测试和主线不完整，按实际证据评分。

### 7.3 AI项目快速抽查

教师随机选下列三项，学生现场完成：

1. 从问题说到一条AI-REQ及其测试。
2. 登录两种角色，让同一记录走过至少两个状态。
3. 运行全量测试并解释一项异常或权限断言。
4. 用`git diff --stat ai-v0.2 ai-v0.3`说明本版为何出现这些文件。
5. 展示BUG-AI-01，指出AI判断和人工源码证据是否一致。
6. 在干净克隆中启动或说明为何能证明没有漏交文件。

无法演示时先判断是环境故障还是成果缺失；使用T03救援后仍无法复现，才按缺失证据扣分。

## 8. E部分：个人解释与过程真实性（5分）

| 得分 | 表现 |
| ---: | --- |
| 5 | 能独立操作；准确解释路由、模型关系、状态、权限和测试中的随机一项；提交号、错误和结果均来自本人电脑 |

| 3 | 系统和记录基本完整，但只能按步骤操作，解释因果关系较弱 |
| 1—2 | 主要依靠他人代操作或只会展示截图；经提示能复现少量内容 |

对“真实性”有疑问时先做现场复现和问答，不只依据代码相似度。全班手工项目本来就使用同一参考终点，代码一致是课程设计结果；关键是个人Git过程、实际运行记录和理解。

## 9. 必须复核但不宜机械封顶的情况

以下情况标记为“需复核”，由教师结合学校考核规定处理，不自动一刀切：

- 七个标签在极短时间一次性创建，记录册却声称逐日完成；
- 测试截图与当前代码运行数量不一致；
- 多名学生AI项目连系统名称、种子数据、错误和提交号都完全相同；
- 学生项目实际路径是教师终点核对包；
- Git跟踪`.venv`、数据库、真实密码、Cookie或访问令牌；
- 学生不能在自己的电脑重新运行任何核心流程；
- 为了通过测试删除正确断言、权限检查或业务规则。

复核顺序：让学生现场运行→随机解释→查看Git提交与差异→查看记录册实际错误→再形成评分结论。

## 13. 成绩解释示例

### 示例A：代码按讲义复制，但过程扎实

学生七个版本均真实运行并提交，能解释预约状态、权限和测试，文档与验收完整。虽然没有独立手写核心代码，仍可在A、B、C、E获得高分，因为这符合课程目标。

### 示例B：最终页面漂亮，但只有一次提交

AI项目功能较多，但没有需求边界、增量版本、异常测试和人工审查。界面不能替代过程证据，D部分只能按已有功能和少量说明得分。

### 示例C：中途使用终点包恢复
