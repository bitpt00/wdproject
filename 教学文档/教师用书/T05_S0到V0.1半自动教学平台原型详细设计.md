# T05 S0到V0.1半自动教学平台原型详细设计

## 1. 文档目的

本文件定义半自动教学平台第一个最小可用原型。原型只负责引导一名非计算机专业学生，从S0起点得到正式dev-v0.1静态原型，不提前实现数据库、登录、预约保存、审批或管理员功能。

平台原型的成功标准不是“能够自动复制V0.1”，而是学生能够在不手写大段代码的情况下，亲自完成以下学习闭环：

```text
确认起点
→ 识别当前问题
→ 用一道具体选择题作出事前判断
→ 逐步触发代码落地
→ 启动并操作网站
→ 按清单核对亲眼看到的文件和页面变化
→ 用一句话解释URL、路由、模板与静态资源
→ 先设计手工测试，再运行6项自动测试
→ 经历一次故障诊断与恢复
→ 建立dev-v0.1基线并导出个人记录
```

- 教学资源/版本终点核对包/dev-v0.1

## 2. 固定起点与固定终点

### 2.1 S0起点

S0只有3个已跟踪文件：

| 文件 | 作用 | 本阶段是否由学生编写 |
| --- | --- | --- |
| .gitignore | 排除虚拟环境、缓存和个人数据库 | 否，来自冻结起点包 |
| requirements.txt | 锁定Flask 3.1.3和pytest 9.1.1 | 否，来自冻结起点包 |
| 初始化开发环境.bat | 在项目内创建独立虚拟环境并安装锁定依赖 | 否，来自冻结起点包 |

S0不是可运行的网站。C0通过表示起点正确，不表示已经有软件功能。

### 2.2 dev-v0.1终点

V0.1必须包含13个文件：

| 类别 | 文件 |
| --- | --- |
| S0保留 | .gitignore、requirements.txt、初始化开发环境.bat |
| 应用入口 | VERSION、app.py |
| 页面 | templates/base.html、index.html、labs.html、reservation_form.html |
| 静态资源 | static/style.css |
| 运行与测试入口 | 启动dev-v0.1.bat、运行测试.bat |
| 自动测试 | tests/test_app.py |

终点必须满足：

- 首页、实验室列表和静态预约表单均可打开。
- 列表显示3间内存实验室，其中2间可预约、1间维护中。
- 使用lab=2进入表单时预选人工智能实验室。
- 提交按钮保持禁用，明确表示本版不保存预约。
- 6项自动测试全部通过。
- 13个终点文件与dev-v0.1在文本内容上相同；Windows换行差异按S06的机械核对规则处理。
- Git工作区干净，正式标签为dev-v0.1。

### 2.3 原型明确不做的事情

- 不让学生从空白手写完整Python、HTML或CSS。
- 不在平台中实现V0.2数据库功能。
- 不把S0称为正式V0.0产品版本。
- 不自动替学生完成事前判断、实际核对、一句话结论和测试结果。
- 不把“平台已应用文件”当作学习任务完成。
- 不要求首个原型打包成完全免安装的最终发行版；先验证教学闭环，便携运行时作为后续工程化工作。

## 3. 教师、学生和平台的总体分工

| 阶段 | 教师专注 | 学生必须完成 | 平台保障 |
| --- | --- | --- | --- |
| 起点 | 讲S0为什么只是准备 | 检查3个文件、环境和版本状态 | 创建隔离个人工作区并核对起点 |
| 骨架 | 讲最小可运行版本和请求链 | 预测目录、触发创建、启动和访问 | 应用验证过的完整文件，检查语法和端口 |
| 页面 | 讲模板、导航、循环、判断和原型边界 | 查看变化、逐页操作、指出代码职责 | 应用页面与样式，显示差异和可见结果 |
| 测试 | 讲预期、实际、手工和自动测试 | 先写用例，再手工执行和运行自动测试 | 检查用例字段，执行pytest并解释输出 |
| 故障 | 讲诊断顺序和恢复边界 | 观察、分类、说明原因、触发恢复和回归 | 注入可恢复故障，提供分级提示和精确恢复 |
| 版本 | 讲提交、标签和里程碑 | 查看差异、输入提交说明、确认标签 | 安全执行Git，阻止错目录和不合格终点 |

### 3.1 学生任务页交互原则

任务页不能把教师的教学设计直接变成三个并列文本框。每个C0—C8关卡固定采用六步向导，并且一次只显示当前一步：

1. **先作判断**：用一道三选一问题建立预期；这一步不是考试，提交后才显示解释。
2. **生成变化**：明确本次新增和修改范围，再由平台应用准确文件；C0起点自动完成。
3. **亲手体验**：显示不超过3项的动作清单和对应入口，学生必须主动确认已经操作。
4. **核对现象**：以可观察、可勾选的结果代替空泛作文；未全部确认不能继续。
5. **说清原理**：只填写一句话，并提供句首框架和不应照抄的参考句式。
6. **完成本关**：平台核对文件和行为，通过后直接打开下一关。

保存动作必须同时产生三种反馈：显示刚才保存的内容、显示保存成功状态、明确下一步。观察表单在操作确认前不出现，解释表单在观察保存前不出现。“教师讲解要点”默认折叠，只用于课堂讲解和课后复习。

测试页遵循同一原则：C0—C5访问时只提示尚未进入测试阶段；C6只显示运行空测试集；C7一次展开一项手工测试，平台提供前置条件和操作，学生填写预期、实际和结论；5项完成并加入自动测试文件后才显示6 passed任务。

## 4. 原型系统结构

平台采用本地浏览器形式，与学生正在构建的V0.1网站相互独立：

```text
浏览器
├─ 教学平台：http://127.0.0.1:8000
│  ├─ 单一当前动作与六步进度
│  ├─ 学生事前判断、实际核对和一句话结论
│  ├─ 检查点执行与恢复
│  ├─ 测试与学习记录
│  └─ 教师查看入口
│
└─ 学生项目：http://127.0.0.1:5001
   └─ S0逐步形成的V0.1网站

教学平台程序
├─ 读取C0—C8任务定义
├─ 读取经过验证的检查点包
├─ 维护学生状态和操作日志
├─ 管理学生项目进程
├─ 调用pytest和Git
└─ 导出个人学习证据包
```

平台端口固定优先使用8000，学生项目优先使用5001，避免与V0.1原始启动脚本的5000端口冲突。平台通过create_app启动学生项目时关闭debug和自动重载，不修改冻结app.py。

## 5. 工作区与安全边界

### 5.1 目录约束

原型只允许在平台自己的工作区根目录内创建个人目录：

```text
teaching_platform/runtime/workspaces/学号/
```

学生输入的学号只允许英文字母、数字、下划线和短横线；姓名只写入学习记录，不参与路径拼接。

### 5.2 平台可管理的路径

平台只管理C0—C8清单中明确列出的13个终点文件、static、templates和tests目录。不得递归删除工作区根目录、课程仓库、用户目录、其他学生目录、.git或.venv。

### 5.3 恢复规则

- 应用检查点前保存平台状态和本轮差异。
- 局部恢复只覆盖当前检查点管理的文件。
- 回到较早检查点时，只处理清单中明确属于后续步骤的文件。
- .git和.venv始终保留。
- 故障注入前把准确文件备份到平台runtime目录，不进行不可恢复删除。
- 每次恢复都记录原因、范围、恢复前现象和恢复后验证结果。

## 6. 学生状态数据

每名学生使用一个JSON状态文件，至少包含：

| 字段 | 内容 |
| --- | --- |
| profile | 学号、姓名、创建时间 |
| workspace | 受控工作区绝对路径 |
| current_checkpoint | 当前已应用的C0—C8检查点 |
| tasks | 每步选择、操作确认、观察清单、一句话结论、保存时间、验证和完成状态 |
| actions | 应用、启动、停止、测试、故障和恢复事件 |
| test_cases | 学生填写的手工测试用例与实际结果 |
| test_output | 最近一次pytest输出、退出码和测试数 |
| git_result | S0提交、V0.1提交和标签证据 |
| export_result | 最近一次个人记录导出位置和时间 |

状态文件使用临时文件写入后原子替换，避免程序中断留下半个JSON文件。

## 8. C0：确认S0起点

### 8.1 教师讲解

讲清“环境准备、版本基线和软件功能”是三件不同的事情。S0已经可以保存开发起点，但没有app.py，所以还不能提供网站。

### 8.2 学生操作前思考

- 当前3个文件分别解决什么问题？
- 为什么.venv和个人SQLite不应该提交？
- 没有app.py时，浏览器能否访问本项目？为什么？

### 8.3 学生必须亲手操作

1. 输入本人学号和姓名，创建个人工作区。
2. 打开文件清单，逐项查看3个起点文件。
3. 查看平台显示的Python、Flask和pytest版本。
4. 查看S0 Git提交和工作区状态。
5. 用自己的话记录“当前为什么还不是一个网站”。

### 8.4 平台动作

- 从冻结S0起点包复制3个文件。
- 在受控个人目录初始化Git并建立S0提交。
- 检查没有跟踪.venv、缓存或数据库。
- 记录每个文件的规范化文本哈希。

### 8.5 可见结果与门禁

文件清单恰为3个，Git工作区干净，尚无dev-v0.1标签。学生完成选择题、亲手查看3个文件、勾选实际结果并写出一句话结论后，才能进入C1。

### 8.6 故障与恢复

若个人目录已经存在，平台不得覆盖；要求学生选择“继续本人进度”或新建另一个合法学号工作区。若起点文件异常，只恢复这3个文件，不删除.git。

## 9. C1：建立项目结构

### 9.1 教师讲解

从“一个文件夹”讲到“按职责组织的项目”。目录结构不是为了好看，而是让Flask知道去哪里找模板和静态资源，也让测试与生产代码分开。

### 9.2 学生操作前思考

把以下对象放到正确位置：Python入口、HTML页面、CSS样式、自动测试。学生提交后平台才显示准确结构。

### 9.3 学生必须亲手操作

1. 在平台中依次选择并创建static、templates和tests。
2. 展开目录树，确认目录位于个人项目根目录。
3. 说明每个目录将保存什么。
4. 尝试判断此时是否应该运行网站。

### 9.4 平台动作

只创建3个空目录并记录事件，不增加任何源文件，不伪造页面结果。

### 9.5 可见结果与门禁

页面暂时没有变化，网站仍不能启动。门禁是3个目录存在、位置正确、学生能说明“只是准备结构”。

### 9.6 故障与恢复

若目录同名文件阻止创建，平台显示冲突路径并提供局部恢复；不得删除来源不明的同名文件，必须先要求学生确认。

## 10. C2：建立最小Flask应用

### 10.1 教师讲解

只讲最短请求链：Python执行app.py，Flask监听本机端口，浏览器向根地址发GET请求，路由函数返回一行文字。暂不讲模板。

### 10.2 学生操作前思考

- 网站入口应该放在哪个文件？
- 根地址应对应哪条路由？
- 成功后浏览器和终端分别应看到什么？

### 10.3 学生必须亲手操作

1. 选择加入VERSION和最小app.py。
2. 打开app.py，指出Flask对象、根路由和启动位置。
3. 点击“启动学生项目”。
4. 亲自打开学生项目地址并刷新一次。
5. 返回平台停止服务，记录浏览器与平台日志中的现象。

### 10.4 平台动作

- 使用S06第4.3节的完整临时app.py，不自行优化。
- 先做Python语法检查，再以当前运行时启动create_app，端口使用5001。
- 检查根地址返回200和“校园实验室预约系统 dev-v0.1”。

### 10.5 可见结果与门禁

浏览器只显示一行纯文字。学生必须解释这证明了服务器和路由可以工作，但尚未使用HTML模板和CSS。

### 10.6 故障与恢复

端口占用由平台选择备用端口并明确显示；语法或文件异常时显示准确文件和检查结果，允许恢复C2，不覆盖S0和.git。

## 11. C3：准备共享布局、首页和样式

### 11.1 教师讲解

讲公共布局、子模板和CSS分别解决重复页面骨架、页面内容差异和显示效果问题。同时强调“文件已经存在”不代表程序已经调用它。

### 11.2 学生操作前思考

预测base.html、index.html和style.css分别属于哪个目录；预测应用后浏览器是否立刻变成完整首页，并说明理由。

### 11.3 学生必须亲手操作

1. 触发加入style.css、base.html和index.html。
2. 在文件观察器中查看extends、block、url_for和样式链接所在位置。
3. 再次启动C2应用并访问根地址。
4. 记录页面仍为纯文字，而不是完整首页。
5. 说明还缺少哪一层连接。

### 11.4 平台动作

从dev-v0.1终点资源复制三个完整文件；继续保留C2临时app.py，不提前应用最终路由。

### 11.5 可见结果与门禁

文件树增加页面与样式，但浏览器仍显示纯文字。门禁要求学生明确“模板尚未被render_template调用”。

### 11.6 故障与恢复

文件扩展名或目录异常时只恢复C3三个资源；样式文件不在本课手工编辑，避免把551行CSS变成课程重点。

## 12. C4：准备实验室列表模板

### 12.1 教师讲解

用实验室卡片解释Jinja2循环和判断：循环把多条数据变成多张卡片，判断根据状态决定显示链接还是“当前不能选择”。

### 12.2 学生操作前思考

- 模板中的labs数据应由谁提供？
- 没有对应路由时，单独增加labs.html能否通过浏览器访问？
- “维护中”为什么不显示可预约链接？

### 12.3 学生必须亲手操作

1. 触发加入labs.html。
2. 指出for循环、状态判断、名称、位置和容量显示位置。
3. 查看当前路由清单，确认尚无/labs正式路由。
4. 记录本步只有文件准备，没有新增可访问页面。

### 12.4 平台动作

复制dev-v0.1准确labs.html，显示该文件需要labs数据以及lab_list、reservation_form路由，但不提前加入最终app.py。

### 12.5 可见结果与门禁

浏览器页面不发生明显变化。学生能说明模板不能自行查询数据，也不能自行成为网址，才进入C5。

### 12.6 故障与恢复

若学生误以为文件名就是网址，平台先提示查看路由清单，不直接给答案；需要恢复时只覆盖labs.html。

## 13. C5：形成完整V0.1页面

### 13.1 教师讲解

把前面准备好的页面一次连接起来：最终app.py提供3条路由、3条内存数据、全局版本值和查询参数。强调内存示例数据不是SQLite持久化。

### 13.2 学生操作前思考

- 最终app.py至少需要哪3条路由？
- 实验室数据应从哪里传给labs.html？
- lab=2怎样影响预约表单的下拉框？
- 表单按钮为什么必须保持禁用？

### 13.3 学生必须亲手操作

1. 触发加入reservation_form.html并用最终app.py替换临时入口。
2. 打开文件差异，确认字符串响应变为render_template。
3. 启动学生项目，依次访问首页、/labs和/reservations/new?lab=2。
4. 从人工智能实验室点击“填写预约信息”。
5. 填写表单并确认按钮不能提交。
6. 停止服务，记录3间实验室和预选结果。

### 13.4 平台动作

- 使用dev-v0.1准确app.py和reservation_form.html。
- 做语法检查、路由检查和三个URL的HTTP检查。
- 记录学生亲自访问的页面，不替学生完成导航。

### 13.5 可见结果与门禁

三个正式页面、共享导航、样式、3条实验室数据和lab=2预选均正确。学生必须解释路由、模板、内存数据和查询参数的关系，并说明本版不保存数据。

### 13.6 故障与恢复

本步提供可恢复的TemplateNotFound教学故障。学生先记录页面和错误名称、判断模板目录，再允许恢复C5并重新访问三个页面。

## 14. C6：增加运行与测试入口

### 14.1 教师讲解

批处理脚本把固定的目录检查和运行命令封装为入口，但脚本本身不是业务功能。启动入口负责运行网站，测试入口负责调用pytest，两者目的不同。

### 14.2 学生操作前思考

比较“启动系统”和“运行测试”会调用什么命令、产生什么结果。预测此时执行测试脚本为什么还不会得到6项测试。

### 14.3 学生必须亲手操作

1. 触发加入启动dev-v0.1.bat和运行测试.bat。
2. 查看两个脚本共同的目录与虚拟环境检查。
3. 通过平台启动入口运行网站并访问首页。
4. 点击测试入口，观察尚无测试文件时的结果。
5. 说明“测试工具存在”和“测试用例存在”的区别。

### 14.4 平台动作

复制dev-v0.1准确批处理文件；平台在MVP中用当前Python运行时执行等价命令，同时完整显示原脚本内容，不要求学生双击隐藏错误窗口。

### 14.5 可见结果与门禁

网站仍正常。运行测试可能显示未收集到测试，不把它标成系统故障。学生解释测试入口与测试内容的区别后进入C7。

### 14.6 故障与恢复

若运行时不可用，平台把它归入环境故障并提供明确路径；只恢复C6两个脚本，不改应用和页面。

## 15. C7：设计并运行V0.1测试

### 15.1 教师讲解

讲“测试是比较实际和预期”，并把状态码200、页面内容断言、测试夹具和参数化分别对应到V0.1场景。不展开pytest高级语法。

### 15.2 学生操作前思考

学生先为首页、列表、预约表单和导航写至少4条手工测试，字段必须包含前置条件、操作、预期、实际和结论。至少一条用例要说明V0.1不能保存预约。

### 15.3 学生必须亲手操作

1. 填写手工用例预期后，触发加入tests/test_app.py。
2. 启动网站，依次执行5项S06手工验收并填写实际结果。
3. 停止网站，点击运行自动测试。
4. 打开测试解释页，选择一项测试并说明它验证什么。
5. 解释为什么4个测试函数可以形成6项测试。

### 15.4 平台动作

- 复制dev-v0.1准确测试文件。
- 预期未填写时拒绝运行全量测试。
- 执行pytest -q，保存退出码、完整输出、测试数和时间。
- 把测试名称对应到首页、实验室、表单和三页导航业务结果。

### 15.5 可见结果与门禁

5项手工验收有实际结果，自动测试显示6 passed。学生能解释一项断言和参数化，才能进入C8。

### 15.6 故障与恢复

若测试数不是6，平台先显示收集到的测试和缺失文件，不直接覆盖；学生完成诊断后可恢复C7测试文件并重新运行。

## 16. C8：故障恢复、终点核对和版本冻结

### 16.1 教师讲解

讲清终点核对、回归测试、提交和标签的先后关系。真实项目中只有代码、功能、测试和版本证据同时满足，才能宣布里程碑完成。

### 16.2 学生操作前思考

- 如果首页模板缺失，会出现什么现象？
- 恢复文件后为什么还要重新运行全部测试？
- 提交和dev-v0.1标签分别留下什么证据？

### 16.3 学生必须亲手操作

1. 触发一次“首页模板缺失”的受控教学故障。
2. 启动或验证项目，记录TemplateNotFound现象。
3. 在分级提示中先选择问题类型并填写判断依据。
4. 触发恢复到C7准确状态。
5. 重新完成关键页面检查和6项回归测试。
6. 查看13文件核对结果和V0.1差异。
7. 输入提交说明，确认建立dev-v0.1标签。
8. 导出本人学习证据包。

### 16.4 平台动作

- 故障注入前备份templates/index.html，随后暂时移出受控工作区。
- 记录故障、提示、学生判断、恢复和回归全过程。
- 使用规范化文本比较核对13个文件，兼容LF/CRLF但不忽略内容差异。
- 只有全部门禁通过才提交和建立标签。
- 生成包含学习记录、状态JSON、测试输出和文件核对表的ZIP证据包。

### 16.5 终点门禁

- 13个文件核对通过。
- 5项手工验收完成。
- 最近一次自动测试为6 passed。
- 至少一次受控故障有观察—判断—恢复—回归记录。
- C0—C8的预测、观察和解释均已填写。
- Git工作区干净，dev-v0.1指向当前提交。
- 个人证据包能够下载并重新打开。

## 20. 从全新学生目录进行最终验收
