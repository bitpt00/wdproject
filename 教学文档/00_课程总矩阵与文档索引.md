# 《软件项目开发》课程总矩阵与文档索引

## 1. 文档定位

本课程面向非计算机专业学生，共32课时，连续4天实施，每天8课时，每课时45分钟。课程使用“校园实验室预约与审批系统”作为贯穿案例。

课程不是以熟练编写Python代码为主要目标，而是让学习者完整经历：

```text
认识最终产品
→ 配置开发环境和使用工具
→ 问题定义与可行性分析
→ 需求分析
→ 系统设计与UML建模
→ 七次增量开发
→ 测试与缺陷修复
→ 集成、验收和发布
→ 使用AI完成一个同类项目
```

七个正式代码版本是七个固定终点；`S0`是进入第一个版本前的固定起点包，不计入正式版本数量。

## 2. 总体教学原则

1. **先整体、后局部**：第一课先体验最终系统，建立对课程、产品和生命周期的整体认识。
2. **一个案例贯穿到底**：原理、UML图、代码、测试和Git版本均使用同一个系统解释。
3. **固定起点、固定终点**：每个开发章节明确起点版本、终点版本和完成标志。
4. **操作可以复现**：每一步明确文件、完整代码、运行方法和预期结果。
5. **操作之后理解原理**：先完成一个可观察的结果，再用刚刚使用的代码解释知识。
6. **测试伴随开发**：每个版本完成后都执行版本测试，`dev-v0.6`集中学习测试设计，`dev-v1.0`执行验收。
7. **Git保存真实过程**：每个终点都提交并建立标签，使开发过程可查看、可比较、可恢复。
8. **逐章质量门禁**：当前文档未检查通过，不进入下一文档。
9. **半自动但不代替思考**：平台可以落地准确代码和执行机械检查，学生仍须预测、操作、观察、测试、诊断和解释。

## 9. 文档质量门禁

每份文档完成后按以下顺序检查，全部通过后才开始下一份：

### 9.1 内容边界检查

- 是否只使用当前章节已经出现的知识、文件和功能。
- 是否没有提前引用后续版本的路由、模型或页面。
- 是否和32课时矩阵分配一致。
- 是否避免重复完整讲解已经掌握的知识。

### 9.2 初学者可读性检查

- 是否先说明解决什么问题，再给技术名词。
- 所有命令是否标明执行目录。
- “创建”“修改”“替换”“追加”是否表达准确。
- 每一步是否有可以观察的结果；没有页面变化时是否明确说明。
- 常见错误是否放在可能发生错误的步骤附近。

### 9.3 操作可复现检查

- 从规定起点实际执行全部步骤。
- 使用锁定的依赖版本，不使用未限定版本的安装命令。
- 每个中间检查点都能启动或明确说明暂时不能启动的原因。
- 终点页面、路由、数据库和测试结果与目标一致。
- 修改型练习执行后能够恢复，不影响后续步骤。

### 9.4 源码一致性检查

- 最终文件名、路径、变量名、路由和版本号与Git标签一致。
- 最终代码核对版由真实源码生成或机械比对。
- 对应标签可以运行规定的测试。
- CSS、图标等不适合逐行粘贴的资源明确说明来源和复制方法。

### 9.5 教学可实施性检查

- 讲解、演示、操作、练习和测试能在分配课时内完成。
- 外专业学习者不需要自行补写关键代码。
- 掉队学习者能够从上一终点基线重新进入。
- 本章提交物可以被教师快速检查。
